# Последовательное распределение симуляций: искусственный стенд

Дата: 2026-11-18. Это developer-only эксперимент с известной истиной. Боевой движок, public JSON/UI, действующий score и продуктовые допуски не меняются. Перед новым дорогим игровым сравнением отдельно проверяются покрытие пространства и статистический выбор среди посещённых составов.

## Протокол до серии

`tools/search_allocation.py` содержит oracle/наблюдения/две политики, `tools/benchmark_search_allocation.py` — воспроизводимый прогон и агрегаты. Search получает только candidate ID, объявленную постоянную стоимость одного наблюдения и сам результат. Истинные вероятности/длительности доступны oracle и последующему evaluator. Нет зависимости от книжного каталога или идентификаторов игровых NPC.

Восемь задач, по32варианта: плавная зависимость; единственная узкая цель; плато; развороты; конфликт целей вероятности/длительности; информативные неизвестные исходы; неодинаковая стоимость; недостижимая цель с остановками по лимиту. В исследовательских fixtures цель50%,5раундов, описательные допуски±10п.п./±1раунд. Это не новые defaults/книжные правила. В duration-conflict сохранён прежний лексикографический приоритет вероятности: joint hit диагностируется, но не подставляется новой objective.

Панель замораживается:64seed indices0–63, budgets112/256/512, pools6/12/24, uniform/racing —9216поисков. Для case/seed одна перемешанная очередь кандидатов и парные indexed tapes на candidate/stage. Порядок выполнения политик не меняет наблюдения; confirmation имеет отдельный stream. Это воспроизводимые синтетические Bernoulli-наблюдения, не детерминированная замена вероятностей. Детерминированные unit cases отдельно проверяют identities/accounting и полный подсчёт вероятностей бинарных путей.

При одном pool uniform/racing имеют одинаковое покрытие и верхнюю границу ресурса: так изолируется allocation. Изменение размера pool показывает другой компромисс — ширину и точность. Оно не доказывает качества генерации новых игровых составов; surrogate/proposer в этом стенде отсутствует. Seeds/fixtures являются development-панелью, без отдельной статистической проверки обобщения на игровые партии.

## Ресурс и алгоритмы

Work cap равен budget×максимальной объявленной стоимости в задаче. Cost1обычный, в variable-cost центральная область имеет cost4. Это условные единицы фиксированной стоимости, не wall time/ETA игры. Обе политики удерживают одинаковый для данного pool резерв: до2финалистов×32свежих наблюдения×максимальная стоимость pool. Неиспользованный reserve показан и не возвращается одной политике тайно. При112/cost1/pool6 uniform точно воспроизводит6×8+2×32. С увеличением budget растёт search, confirmation остаётся32на финалиста; это сознательная фиксация для сравнения allocation, не рекомендуемый окончательный автоплан.

Uniform даёт всем одинаковую целую квоту, остаток распределяет по кругу с учётом доступного ресурса. Racing сначала касается всех кандидатов, до4наблюдений каждому (при широком pool — меньше, чтобы уложиться). Затем порциями до4выбирает минимальную оптимистическую ошибку относительно target; при равенстве — максимальную ширину интервала ошибки, делённую на sqrt(cost), затем меньшее n/ID. Недоступный по текущим bounds кандидат не удаляется навсегда. После исключения прежнего лидера по unknown eligibility пересчитывается. Это явно заданный исследовательский allocation index; оптимальность или superiority из существующей bandit-теоремы ему не приписываются.

Обе политики выбирают до2финалистов по прежнему point score: ошибка доли побед, затем ошибка наблюдаемой длительности, затем порядок pool. После свежей confirmation ранжирование повторяется, actual unknown исключает конкретный source. Бюджет/все знаменатели/неполученная рекомендация остаются видимы.

## Последовательные интервалы

Для Bernoulli stream с sуспехами в nнаблюдениях инвертируется смесь likelihood ratios:

`M_n(p) = B(s+1/2,n-s+1/2) / (B(1/2,1/2) p^s (1-p)^(n-s))`.

Confidence set — `M_n(p) <= 1/alpha`. Вычисление через log-gamma и outward bisection; n0даёт[0,1], endpoints учитываются явно. Основание — mixture martingale и неравенство Ville; bounds допускают последовательный просмотр/остановку. [Howard и соавторы, confidence sequences](https://arxiv.org/abs/1810.08240), [раздел о Bernoulli mixtures](https://arxiv.org/html/1810.08240v9#S3.SS2).

При unknown используются Y=confirmed win и Z=confirmed win или unknown: `E[Y] <= p <= E[Z]`. Даже информативное missing не требует деления на n−unknown. Нижняя CS для Y и верхняя для Z образуют bounds полной вероятности. Error budget `.05/(4*K)` на stream учитывает фиксированный K, два stages и две bounding streams. Union bound защищает все arms/stages/последовательные просмотры внутри **одного** поиска. Он не обещает совместного95%покрытия всех9216запусков. Отдельного confidence certificate длительности/отсутствия будущих unknown здесь нет. Единственная статистическая сертификация — включение всего final win interval в описательную полосу цели.

Математическая корректность CS не доказывает качество allocation: для него сравниваются фактические результаты. Задачи fixed-budget thresholding изучаются отдельно, но теорема другой objective не переносится на этот index. [Locatelli и соавторы](https://proceedings.mlr.press/v48/locatelli16.html).

## Метрики и ограничения

- Win/joint coverage: посетили ли хотя бы один source с подходящей истинной вероятностью/обеими целями и нулевой истинной частотой unknown.
- Best visited error и selection regret: выбрали ли лучший из посещённых допустимых по истине вариантов. Нулевой regret при нулевом coverage не считается решением.
- Final win/joint hit после confirmation, missing recommendation, выбор source со скрытым unsupported risk, actual unknown/round-limit counts.
- Для missing/unsafe selected применяется явный worst-error penalty `max(target,1-target)`; безусловные средние содержат все64запуска. Nullable ordinary regret не усредняется с выкидыванием неудач.
- Work/trials/unused reserve, bounds coverage во всех записанных decision checkpoints и win-band certificate. Наблюдаемое prefix mean при unknown не объявляется полной длительностью: oracle truth хранится отдельно; round-limit использует bounded15раундов.

Сравнения uniform/racing парные по case/seed/budget/pool. Размер pool меняет и покрытие, и число наблюдений на состав; выводы по ним приводятся отдельно. Не выбирать понравившиеся ячейки или новый index после панели. Никакая величина улучшения на этих игрушечных задачах сама по себе не разрешает внедрение в игру или новый тяжёлый MC-прогон. По результату нужен один следующий эксперимент; допуски/совместная цель/новые public поля при необходимости согласуются отдельно.

## Решение и следующий исследовательский шаг

Стенд принят как дешёвый engineering-инструмент. Игровой поиск/score/допуски/публичный контракт прежние. Математический компонент CS проверен и доступен только в tools; index racing по этой панели не рекомендован для внедрения.

Следующий протокол — раздельно планировать adaptive search и независимую final confirmation. До её первого наблюдения фиксировать число mфиналистов и nпрогонов по запрошенной точности/доступному ресурсу. Для fixed-n final bounds достаточно correction по этим m, а не по всем исходным K; при unknown сохраняются две Y/Z streams. m/error budget определяются **до** исходов и не уменьшаются после исключений. Если nвыбирается по screening, это допустимо при свежей независимой confirmation; остановка/добавление по её собственным результатам снова требует CS или заранее заданного spending. Публичный режим и игровые значения отсюда автоматически не следуют.

Сначала проверить этот отдельный протокол на стенде, включая недостаточный бюджет/узкую цель/недостижимость и power в интерьере полосы. Не подгонять текущий index после панели и не повторять игровые42/202прогоны до содержательного результата. Совместную цель по раундам/победе и допуски согласовать перед изменением production score. Это один следующий эксперимент, а не обещание оптимального состава или фиксированного ускорения.

Продолжение завершено отдельно: [fixed-n precision planning](confirmation-planning-2026-11-18.md), включая31checks/legacy parity и новую парную панель. Исторические hashes этой первой панели сохраняются; текущий tools модуль расширен, legacy observations/results проверены отдельно.
