# Динамический генератор: поиск и профиль после ADR-0125

Дата: 2026-11-16. Реальные последовательные запуски, без изменения игровых правил, source guards, seed scheme или согласованного ранжирования. Это ограниченный baseline демонстрационных партий, не результат для партии пользователя и не доказательство качества полного генератора.

## Входы и методика

[Harness поиска](../../tools/benchmark_dynamic.py) использует текущие публичные примеры: два melee-PC из `search.request.json`; стрелок со Щитом (Shield), запасным Мечом (Sword) и melee-союзником из `pc-ranged.request.json`; та же группа с магом из `elemental-mage.request.json`. У мага уровень4, Разум (Reason)3 и Сила воли (Willpower)6; это сильный пример, не стандартный начинающий персонаж. Нет самостоятельно придуманной тактики или новых правил для benchmark.

Каждый из трёх входов выполнен на master seeds42 и101. Условия одинаковы: NPC1–5, неподвижная Close-сцена, цель50%побед/5начатых раундов, предел15раундов. Малый план:4кандидата×4screening-боя +2финалиста×16независимых validation-боёв =48trials. Всего6поисков/288trials; диагностические повторы unsupported, если есть, учитываются отдельно. Это существенно меньше обычного автоплана UI и не покрывает верхнюю границу10NPC.

Импорты и parse/admission входа выполнены до таймера поиска; сборка составов, симуляция и проверка результата application входят в таймер. JSON encoding/source/schema readmission измерены отдельно. HTTP, rendering, отдельный прогрев, память и process backend в этом baseline не измерялись. Запуски последовательные, тяжёлые тесты одновременно не выполнялись; частота CPU и посторонняя нагрузка ОС не фиксировались. На каждом seed один search-run, это не медианы повторов времени.

Среда: CPython3.12.4, Windows11 build26200, AMD64 Family23 Model113 Stepping0. SHA-256 всего `src/**/*.py` до оптимизации: `ec62ce1bc433666d73343d0a4a097f822224264e89a8c5d6937eae05d876f5a6`; harness: `f6699ca340ddbdf62bcd9af2be0cda97a11adf1bbea63a405be42fddd3d377eb`. Алгоритм hash: упорядоченные relative POSIX paths, NUL, исходные bytes файла, NUL. Сырые входы, resolved space, полный result/replay и batch timings — `.cache/dynamic-baseline-2026-11-16.json`.

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe tools/benchmark_dynamic.py --output .cache/dynamic-baseline-2026-11-16.json
.venv/Scripts/python.exe tools/profile_dynamic.py .cache/dynamic-baseline-2026-11-16.json --output .cache/dynamic-profile.txt
```

Команды заново измеряют текущую версию. Для сравнения версий использовать новый output path и те же сохранённые входы; времена ниже относятся к указанному baseline, не к будущей версии кода.

## Результаты поиска

Во всех строках исполнено48trials. Показан первый финалист после независимой validation, а не лучший screening point estimate.

| Партия | Seed | Поиск, с | NPC в четырёх screening-составах | Победы финалиста | Средние раунды |
| --- | --- | ---: | --- | ---: | ---: |
| Два melee-PC |42|32.161|3/3/3/3|100.0%|3.8125|
| Два melee-PC |101|73.072|5/5/5/5|93.75%|6.3750|
| Стрелок + melee-PC |42|96.754|3/3/3/3|100.0%|4.1875|

| Стрелок + melee-PC + маг |101|192.132|5/5/5/4|100.0%|3.1875|

Сериализация заняла0.115–0.501s, значительно меньше поиска. Наблюдаемые исходы всех288боёв:284победы партии,4поражения,0round limits,0unsupported. Ноль observed unsupported не доказывает их отсутствия у этих составов или покрытия всех Miscasts; диагностировать конкретную новую причину по этой выборке не удалось. Известные неподдержанные продолжения магии сохраняются.

Цель50%не достигнута ни в одном из этих коротких поисков. Для16/16побед Wilson95%=80.64–100%, для15/16=71.67–98.89%: финалисты действительно выглядят слишком лёгкими на этой выборке. Это не доказывает отсутствие подходящего состава в пространстве параметров. Четыре candidates почти не охватили диапазон численности; даже две близкие по длительности рекомендации могут существенно промахиваться по сложности.

Есть заметный screening→validation drift: у melee/seed101 выбранный состав получил3/4побед на screening и15/16после независимой проверки. Повышать точность только финалистам недостаточно, если короткий поиск не предлагает достаточно разнообразных кандидатов. Текущая лексикография сохраняется: сначала отклонение доли побед, затем длительности; менять эти приоритеты без отдельного решения не следует.

## Профиль одного боя

[Profiler](../../tools/profile_dynamic.py) выбрал `mixed-magic/101`, состав `dynamic:explore:2`, trial0:14действий/3начатых раунда. Обычный запуск3.060s, профилируемый9.529s; времена cProfile нельзя использовать вместо обычного wall time. Полные native-журналы обоих запусков совпали. Это профиль одного наблюдённого состава, не всех288боёв.

| Функция | Вызовы | Cumulative, с |
| --- | ---: | ---: |
| `select_pc_tactic` |127|7.122|
| вложенная `incoming_risk` |1507|3.866|
| `validate_pc_book_npc_definition` |13977|1.681|

Cumulative строки перекрываются, их нельзя суммировать. Около75%профилируемого времени проходит через автоматическую тактику; основные повторные входы идут из выбора action/target, repeater mode, unsupported/swap/Shield guards и canonical replay. Отключение этих проверок или повторное использование решения после изменения состояния было бы неверным ускорением.

Дополнительно найден небольшой самостоятельный участок: каждый вызов `validate_pc_book_npc_definition` линейно перебирал59книжных identities даже для generated NPC с собственным source. Это работа существующего каталога, а не необходимое сравнение всех книжных противников при динамической генерации.

## Реализованный индекс каталога

В [валидаторе](../../src/towr/domain/pc_npc_catalog.py) добавлены два неизменяемых индекса identity/source→ordinal. Для обычных exact-str выбирается первый совпавший профиль в прежнем порядке каталога; definition/attack/Protection source claims проверяются вместе. Для строковых subclasses/Enum и нестандартных equality/hash сохранён прежний matcher. `_definition` по-прежнему строит новый канонический граф, `_require_canonical_types` и reserved-ID отказ сохранены. Кэширования бойцов, результатов или состояния боя нет; правила и публичные поля не изменились.

После изменения source SHA-256: `1fa1f99ae544e49f8b314613be5b6919dd593b754bb1c4cc49e29614c9949959`. На том же фиксированном trial выполнено по три обычных повтора до и после с прогревом; каждый результат сравнивался с полным native-журналом, сохранённым до изменения. Все совпали.

| --- | --- | ---: |
| Линейный поиск |3.056 /3.147 /3.130|3.130|

В этой серии медиана времени меньше примерно на9.9%, отношение медиан1.109. Первый повтор после прогрева оказался выбросом; диапазоны пересекаются, поэтому это локальное наблюдение, не гарантия ускорения любой партии. Дополнительная первоначальная серия после изменения2.904/2.824/2.777s сохранена в `.cache/dynamic-index-comparison.json` вместе с основной; она не подменяет опубликованную серию.

Повторный cProfile:13977вызовов проверки каталога сохранились, cumulative уменьшилось1.681→0.192s. Полные журналы обычного/profile запуска совпали также после изменения. `select_pc_tactic` остался127вызовов и занимает6.053из8.408s нового профилируемого запуска: главный участок затрат сохраняется. Новая серия поиска из288боёв после индекса не повторялась; таблица поиска выше относится к baseline.

Проверки: [7новых source/index случаев](../../tests/unit/test_pc_catalog_identity_index.py) вместе с M21 catalog/generated equipment —31OK/0.380s; [harness](../../tests/unit/test_dynamic_benchmark.py), generated ranged execution и ranged Wizard —15OK/7.901s. Проверены все59канонических профилей, generated fast path, mixed source claims, aliases/bools/custom equality и независимые новые canonical graphs. Full regression/wheel не запускались: изменён lookup, а не контракт или упаковка.

## Вывод для следующей функции

Следующий приоритет — повторные вычисления автоматической тактики, прежде всего одинаковые оценки входящего риска в рамках одного неизменившегося решения. Сохранять source/canonical replay/hand/price guards и полные результаты на тех же seed. Общий cache по неполному snapshot и изменение игровых правил не требуются.

Оценка времени UI пока использует исторический Staff baseline и не учитывает новые PC ranged/magic/talent затраты. По этому маленькому набору нельзя обещать укладывание обычного автоплана в10–15минут. После устранения подтверждённой повторной работы нужна новая калибровка времени и сравнение ширины поиска/точности на одинаковом бюджете; добавление новых именных statblocks проблему не решит.
