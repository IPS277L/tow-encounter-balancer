# Динамический генератор: первый сквозной срез

Генератор сам создаёт NPC, варьируя WS/Strength/Toughness/Agility, Melee/Athletics, Staff/Dagger и Light Armour. Число врагов может быть фиксированным: поиск всё равно меняет их параметры и экипировку. Готовый reserve и книжные NPC не нужны. [Контракт и ограничения](../../decisions/ADR-0113-dynamic-npc-generation-and-adaptive-search.md).

## Локальный UI

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr ui
```

Откройте `http://127.0.0.1:8765/`. Из корня репозитория начальный JSON берётся из рабочего [ui.request.json](ui.request.json). Для своего файла: `towr ui --request path/to/request.json` (ручной план); `--port 8877` меняет порт. Вне репозитория без `--request` можно загрузить файл кнопкой в браузере. Остановка сервера — Ctrl+C в терминале.

Блок «Параметры поиска» сворачивается и по умолчанию закрыт; в заголовке видны текущие цели, план симуляций и приблизительное время. Тот же диапазон времени показан под настройками точности. Внутри форма разделена на «Состав противников», «Цели боя», «Поиск и точность» и отдельную «Воспроизводимость». В целях сначала показаны целевая длительность и предел раундов, затем процент победы; свёрнутая строка следует тому же порядку. Seed вынесен в компактный ручной блок, отдельно от четырёх настроек автоплана. Она редактирует количество NPC, целевую вероятность победы игроков в процентах, длительность, seed и бюджет. Изменения формы обновляют JSON; корректные ручные изменения JSON отражаются в форме. В блоке запроса переключатель «Карточки / JSON» открывает два представления одних данных. Карточки позволяют менять характеристики, навыки, оружие и хват персонажей; для противников — наборы значений через запятую, оружие, броню и варианты способностей. Судьба, тактика и дополнительные параметры вынесены в раскрывающиеся разделы. Добавление новых персонажей/сложных записей можно выполнить в JSON. Переключение не меняет скрытые поля и данные. По умолчанию «Автоматический план» подбирает количество кандидатов, предварительных боёв и проверок финалистов по пространству NPC, численности обеих сторон, целевой вероятности и длительности. Снимите флажок для ручной настройки этих четырёх значений. Отдельного поля бюджета нет: текст плана и search.max_total_trials всегда равны candidates×exploration + finalists×validation, включая ручной режим и JSON-правки. При вводе JSON показывается предварительный план; производные числа записываются при завершении редактирования/переключении/сохранении/запуске, чтобы не сбивать курсор.

Загрузка файла запроса также включает ручной план, сохраняя переданные параметры поиска. В заголовке «Запроса» доступны SVG-иконки загрузки, скачивания и форматирования с подсказками; форматирование видно только в JSON-режиме. В «Результате» оставлена только иконка скачивания отчёта. Сверху — только запуск/отмена. Форматирование меняет отступы, а не данные. «Запустить генератор» отправляет текущий текст в тот же строгий parser/поиск, что использует CLI. Во время расчёта виден счётчик времени, редактирование и повторный запуск заблокированы; доступна кнопка «Отменить генерацию». Справа доступны «Карточки / JSON»: финалисты с оценками побед, интервалами, длительностью и составом NPC; остальные исследованные составы раскрываются отдельно. Исходные оценки не редактируются. «Взять за основу запроса» переносит значения NPC в допустимое пространство текущего запроса и фиксирует их число; разные сочетания этих значений остаются возможны, партия и настройки поиска сохраняются. «Скачать бой» сохраняет PC simulation replay, «Скачать результат» — исходный полный отчёт. Любая правка запроса только помечает последний результат как устаревший; он остаётся видимым в обоих режимах. Пересчёт выполняется исключительно кнопкой «Запустить генератор». Возврат к исходным данным снимает пометку без расчёта; невалидный JSON не перезаписывается при попытке переключения. Вкладку можно оставлять открытой во время долгого расчёта. Редактор не сохраняет изменения автоматически: используйте скачивание запроса.

UI обслуживается стандартным Python HTTP-сервером на loopback и допускает один расчёт одновременно. Установка дополнительных зависимостей и сборка frontend не нужны; форма/страница поставляются обычными Python-модулями. Нет новых игровых правил или wire version. История заданий и прогресс по кандидатам выходят за границу этого прототипа.

## Seed и воспроизводимость

Seed задаётся явно в форме или JSON. Он не меняется при запуске/отмене, а переключатель нового seed удалён. Одинаковый seed и полный запрос воспроизводят поиск и его результат; другое значение можно ввести вручную. Фактический seed хранится строкой uint64 в source/report без потери точности. UUID отдельного HTTP-запуска служит только для адресной отмены и не участвует в RNG/отчёте.

## Отмена генерации

После запуска кнопка «Запустить генератор» на том же месте заменяется красной «Отменить генерацию». После завершения/отмены возвращается запуск; во время подтверждения отмены кнопка показывает «Отмена…». Она посылает серверу команду остановки именно текущего HTTP-запуска. Интерфейс показывает «Отмена…» и ждёт фактического завершения; редактирование разблокируется после подтверждения. Это не только прерывание browser fetch: поиск проверяет сигнал перед кандидатами/возвратом, а стандартный simulator — перед бросками. Остановка кооперативная, на ближайшей контрольной точке. Завершённые до отмены части не выдаются как полный результат; скачивание результата недоступно. Можно сразу запустить расчёт заново с тем же seed.

Запоздавшая отмена другого запуска отклоняется. Ранняя отмена, пришедшая до регистрации generation POST, запоминается для его token (ограниченное множество128записей); новый запуск использует другой UUID. Если расчёт уже завершён, интерфейс получает его завершённый результат. CLI JSON families не имеют нового отменённого report: это UI transport control. Python search/execute допускают optional cancel_requested callback; для внешнего custom simulator checkpoint гарантируется между его вызовами, для стандартного — также внутри dice RNG.

## Автоплан и рабочие значения UI

По умолчанию:1–10NPC, цель50%побед игроков, средняя длительность5раундов, предел15раундов. Для исходной партии/пространства автоплан даёт24кандидата ×12предварительных боёв +2финалиста ×256новых боёв = максимум800симуляций. Это вычисляемый план; seed42из файла используется до ручного изменения. Это стартовый компромисс под согласованное ожидание10–15минут, а не гарантированный таймаут. Загруженный файл/--request включает ручной план, сохраняя его четыре управляющих числа; бюджет всё равно выводится автоматически. Seed также сохраняется из запроса. Короткий search.request.json остаётся самостоятельным12-trial smoke-примером для CLI и тестов.

Короткий замер на текущей машине (2PC, одинаковые Staff NPC WS/S/T/Ag3, Melee/Athletics4, без брони, seed42,4боя на состав, предел15):1NPC —0,027с/бой;5NPC —1,081с/бой;10NPC —2,266с/бой. Поиск смешивает разные составы, поэтому800trials могут занять заметно больше или меньше ожидаемого. Полный800-trial замер ради настройки не запускался.

Кандидаты увеличивают разнообразие поиска; предварительные бои дают грубый отсев, а новые бои финалиста уточняют его вероятность победы. При observed50% интервал Уилсона95% для64боёв ≈38–62%,128боёв ≈41,5–58,5%,256боёв ≈43,9–56,1%,400боёв ≈45,1–54,9%. Расчёт по [формуле NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm). Интервалы относятся к фиксированному составу/тактике, не доказывают полноту пространства поиска, надёжность порядка финалистов или точность среднего числа раундов. Для первого подбора выбран256-trial validation; если нужна точность около±5п.п., увеличьте finalist_trials до400 и пересчитайте бюджет.

## JSON/CLI

Запуск JSON/CLI из корня репозитория:

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/search.request.json > generated.json
```

После установки доступна та же команда `towr generate-encounter INPUT`; `-` читает UTF-8 JSON из stdin. [Полный входной пример](search.request.json) содержит только party/facts/day, пространство компонентов, число NPC, цели и бюджет. Нет enemy reserve, target_priority или defeat_decisions в партии. Эти поля создаются при сборке найденных боёв; порядок партии определяет PC activation/NPC target priority, порядок NPC — PC target priority/NPC activation. `defeat_disposition` явно подтверждает общее GM-решение для созданных целей.

JSON family `dynamic_encounter_search`, version1: `search_space` задаёт массив разрешённых значений каждого параметра и массив альтернативных наборов abilities. `npc_count.minimum/maximum` ограничивают численность. `targets.win_rate` и `targets.started_rounds` — сокращённые дроби `{numerator, denominator}`; например3/5 и3/1. Только integer JSON tokens, seed — десятичная строка uint64. Бюджет обязан покрывать `max_candidates * exploration_trials + top_k * finalist_trials`. Первый CLI backend — `execution: {"mode":"sequential"}`. Все поля закрыты; неподдержанные компоненты/режимы и несогласованные значения отвергаются до симуляции.

Пример ограничен3кандидатами ×2trials +2финалистами ×3trials =12trials максимум. Для полезной оценки увеличьте trials и budget: например12×16+3×64=384. Значения smoke-примера демонстрируют формат и воспроизводимость, но дают широкие интервалы.

JSON-результат содержит `source_request` (полный точный вход), `explored`, отдельные `validations`, `selected` (ID только финалистов без observed unsupported), фактические `total_trials`, `proposal_attempts` и `proposal_limit_reached`. Каждый кандидат содержит NPC компоненты, win rate/Wilson95, mean started rounds/Hoeffding95, outcome counts и `replay` — полноценный текущий PC simulation JSON1. Чтобы повторить конкретный бой:

```powershell
$r = Get-Content generated.json -Raw | ConvertFrom-Json
$r.validations[0].replay | ConvertTo-Json -Depth 100 | Set-Content replay.json -Encoding utf8NoBOM
.venv/Scripts/python.exe -m towr simulate-pc-melee replay.json
```

Команды записи рассчитаны на PowerShell7. Ошибки входа дают JSON `dynamic_encounter_search_error` и exit2; сбой исполнения — exit3 без частичного результата; ошибки I/O — exit4. Диагностика идёт в stderr. Схемы [request](../../../src/towr/adapters/schemas/dynamic-encounter-request-v1.schema.json), [result](../../../src/towr/adapters/schemas/dynamic-encounter-result-v1.schema.json), [error](../../../src/towr/adapters/schemas/dynamic-encounter-error-v1.schema.json) разрешаются offline.

Authored Drained-on-hit допускается только явной альтернативой `search_space.abilities: [[], ["drained_on_hit"]]`; по умолчанию `[[]]`. Это разрешённый авторский компонент, не автоматическая выдача книжного таланта. Действующий owner учитывает фактическое попадание и независимый источник Conditions.

Это лучшие найденные приближения к целям при заданной тактике и бюджете. Длительность включает цензурированные round-limit/unsupported префиксы; проверки target tolerance и глобального оптимума нет. Если наблюдался unsupported, такой screening кандидат не проходит в validation; unsupported validation сохраняется в отчёте, но не в selected. Пустой selected — допустимый честный результат.

Python API: `towr.application.dynamic_encounter.DynamicEncounterRequest`, `NpcSearchSpace`, `search_dynamic_encounter`. Simulator можно передать явно; по умолчанию sequential aggregate. Предыдущий [Python-пример](search.py) также работает: он переиспользует партию из M10, отбрасывая прежних enemies. Новый JSON-вход полностью самостоятельный и такого scenario не требует. Расширять нужно составляемые компоненты и их prerequisites, а не список именных statblocks.

Автоплан — ограниченная UI-эвристика, не дополнительное игровое правило и не статистическая гарантия времени. Ширина массива допустимых значений/численности задаёт разнообразие (логарифмическая оценка), а workload использует party size, среднее число NPC, целевые раунды/cap, WS/Ag и наличие способностей. Базовая ёмкость800trials масштабируется по workload в пределах256–1600. Около40%отводится предварительному поиску, с максимум64кандидатами; конечное маленькое пространство ограничивает их число. Validation budget зависит от p(1−p), до2финалистов, обычно64–256боёв, но может быть уменьшен доступной ёмкостью. При50% и базовой нагрузке получается прежний профиль800. Фактический план всегда показывается перед запуском; ручной режим позволяет увеличить точность, если цена приемлема. Это не покрытие всех сочетаний и не жёсткий10–15мин timeout.

Оценка времени UI рассчитывается для полного плана: piecewise linear стоимость боя по замерам1/5/10NPC (0,027/1,081/2,266с,2PC), среднее число противников, партия, target rounds/cap, WS/Ag, abilities и число trials. От центральной оценки показывается широкий ориентир0,6–1,6×, округлённый в секунды/минуты/часы; это не статистический доверительный интервал, ETA прогресса или гарантия. При некорректных параметрах вместо числа показывается «нет оценки». Стандартный профиль даёт примерно10–26мин. На другом компьютере и для других реальных исходов время может отличаться; неполный поиск/unsupported может завершиться раньше. Расчёт оценки не запускает MC и не меняет данные запроса.
