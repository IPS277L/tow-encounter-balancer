# Динамический генератор: первый сквозной срез

Генератор сам создаёт NPC, варьируя WS/Strength/Toughness/Agility, Melee/Defence/Athletics, шесть одноручных оружий, Light Armour и Shield. Число врагов может быть фиксированным: поиск всё равно меняет их параметры и экипировку. Готовый reserve и книжные NPC не нужны. [Контракт и ограничения](../../decisions/ADR-0113-dynamic-npc-generation-and-adaptive-search.md).

## Локальный UI

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr ui
```

Откройте `http://127.0.0.1:8765/`. Из корня репозитория начальный JSON берётся из рабочего [ui.request.json](ui.request.json). Для своего файла: `towr ui --request path/to/request.json` (ручной план); `--port 8877` меняет порт. Вне репозитория без `--request` можно загрузить файл кнопкой в браузере. Остановка сервера — Ctrl+C в терминале.

Блок «Параметры поиска» сворачивается и по умолчанию закрыт; в заголовке видны текущие цели, план симуляций и приблизительное время. Тот же диапазон времени показан под настройками точности. Внутри форма разделена на «Состав противников», «Цели боя», «Поиск и точность» и отдельную «Воспроизводимость». В целях сначала показаны целевая длительность и предел раундов, затем процент победы; свёрнутая строка следует тому же порядку. Seed вынесен в компактный ручной блок, отдельно от четырёх настроек автоплана. Форма редактирует количество NPC, целевую вероятность победы игроков в процентах, длительность и seed. Изменения формы обновляют JSON; корректные ручные изменения JSON отражаются в форме. В блоке запроса переключатель «Карточки / JSON» открывает два представления одних данных. Карточки разделяют характеристики, навыки, снаряжение, таланты и ресурсы персонажа. Можно добавлять/удалять персонажей и отдельные предметы оружия/защиты, назначать начальные руки/ношение, описывать расходники с количеством, добавлять и удалять таланты тегами. Судьба задаётся рейтингом; внутренние ledgers и policies собираются автоматически. Диапазоны NPC по умолчанию выводятся по партии; необязательные ручные ограничения скрыты в отдельном блоке. Условия сцены показаны явно: Close, без засады и terrain modifiers, начало новой сессии с полными ресурсами. Переключение не меняет скрытые поля и данные. По умолчанию «Автоматический план» подбирает количество кандидатов, предварительных боёв и проверок финалистов по пространству NPC, численности обеих сторон, целевой вероятности и длительности. Снимите флажок для ручной настройки этих четырёх значений. Отдельного поля бюджета нет: текст плана и search.max_total_trials всегда равны candidates×exploration + finalists×validation, включая ручной режим и JSON-правки. При вводе JSON показывается предварительный план; производные числа записываются при завершении редактирования/переключении/сохранении/запуске, чтобы не сбивать курсор.

Загрузка файла запроса также включает ручной план, сохраняя переданные параметры поиска. В заголовке «Запроса» доступны SVG-иконки загрузки, скачивания и форматирования с подсказками; форматирование видно только в JSON-режиме. В «Результате» также доступны иконки загрузки и скачивания отчёта, а в JSON-виде — форматирование (слева от остальных иконок). Сверху — только запуск/отмена. Форматирование меняет отступы, а не данные. «Запустить генератор» отправляет текущий текст в тот же строгий parser/поиск, что использует CLI. Во время расчёта виден отдельный блок прогресса, редактирование и повторный запуск заблокированы; доступна кнопка «Отменить генерацию». Справа доступны «Карточки / JSON»: финалисты с оценками побед, интервалами, длительностью и составом NPC; остальные исследованные составы раскрываются отдельно. Исходные оценки не редактируются. «Скачать бой» сохраняет PC simulation replay, «Скачать результат» — исходный полный отчёт. Любая правка запроса только помечает последний результат как устаревший; он остаётся видимым в обоих режимах. Пересчёт выполняется исключительно кнопкой «Запустить генератор». Возврат к исходным данным снимает пометку без расчёта; невалидный JSON не перезаписывается при попытке переключения. Вкладку можно оставлять открытой во время долгого расчёта. Редактор не сохраняет изменения автоматически: используйте скачивание запроса.

В карточках результата убраны общие сводки кандидатов, seed и числа финалистов. Для каждого состава сначала показан отдельный блок статистики с интервалом оценки и исходами, затем отдельные карточки всех противников; одинаковые NPC не объединяются. Показаны все8характеристик и16навыков из Player’s Guide1.4 (гл.II, лист персонажа14; гл.III, Characteristics & Skills68). В запросе и результате поля идут в порядке книги независимо от порядка ключей JSON; используются только книжные сокращения характеристик (WS, BS, S, T, I, Ag, Re, Fel), навыки указаны полными оригинальными названиями. Характеристики и навыки снова разделены: в запросе отдельные сетки полей, в результате отдельные таблицы по два параметра в строке. Пробная группировка характеристики с двумя навыками отменена. Неизвестные значения отмечены прочерком и не выводятся из других характеристик. Экипировка, расходники, таланты и способности в результате показаны тегами: наведите курсор для описания. Редакторы инвентаря в запросе сохраняются. Карточки игроков также показывают все8характеристик и16навыков: ещё не подключённые поля неактивны, отмечены прочерком и не добавляют данных в JSON. Для расходников и талантов пока показаны прочерки; способности при попадании сохраняются отдельной строкой. Заголовок состава и иконка скачивания выровнены с внешними границами последующих блоков. Рядом оставлена только иконка скачивания боя с подсказкой; переноса состава в запрос больше нет. Полный JSON сохраняет все исходные данные.

В двухколоночном режиме верхние границы JSON запроса и результата выровнены; карточка первого игрока и блок статистики первого состава также начинаются на одной высоте. Название первого состава и скачивание боя находятся в полосе над карточкой, напротив пояснения запроса; в JSON-виде они невидимы, сохраняя место в раскладке. Карточки и JSON начинаются на одной линии во всех сочетаниях видов; переключение не сдвигает содержимое. Выравнивание учитывает переносы подсказок и уведомление об устаревшем результате. На узком экране панели идут друг под другом.

Загрузка JSON результата открывает сохранённый отчёт в карточках/JSON и разрешает его скачивание; запрос и seed не меняются, расчёт не запускается. При отличающемся исходном запросе появляется пометка устаревшего результата. Неподходящий JSON или повреждённые данные составов не заменяют текущий отчёт. Форматирование меняет только отступы JSON; во время генерации действия с файлами результата заблокированы, запоздавшая загрузка не перекрывает новый расчёт.

Подсказки тегов собственные: появляются через120мс при наведении, сразу при фокусе с клавиатуры, закрываются по Escape. Подсказку можно удерживать наведением на неё; при прокрутке, смене вида или перерисовке она скрывается. Текст и оформление поддерживают обе темы; браузерный title у тегов убран. Теги результата и талантов запроса используют единые высоту26px, шрифт12px и скругление14px; крестик удаления остаётся внутри тега.

Переключатель темы находится справа сверху. При первом открытии тема соответствует системной; выбранная светлая/тёмная тема сохраняется в браузере для адреса UI. Настройка распространяется на форму, JSON, прогресс, кнопки и карточки; не меняет запрос, seed или результат. Если браузер запрещает локальное хранение, переключение работает до закрытия страницы.

UI обслуживается стандартным Python HTTP-сервером на loopback и допускает один расчёт одновременно. Установка дополнительных зависимостей и сборка frontend не нужны; форма/страница поставляются обычными Python-модулями. Нет новых игровых правил или wire version. История заданий выходит за границу этого прототипа.

### Отдельные файлы игроков и противников

В заголовке каждой карточки есть иконки загрузки/скачивания одного персонажа. В игроке загрузка **заменяет выбранного участника**. Иконка рядом с «Добавить» позволяет загрузить нового игрока в партию. ID в партии должен быть уникален: коллизия оставляет данные без изменений; для замены используйте иконку существующего игрока. Изменение запроса помечает отчёт устаревшим, но не запускает генератор.

Файлы — обычные объекты текущего профиля, без отчёта и дополнительной оболочки: [игрок](player.character.json) и [NPC](npc.character.json). Сохраняются все данные игрока: характеристики/навыки, отдельные предметы и их положение, расходники/количество, таланты и Fate. Неактивные плейсхолдеры не записываются. Можно сохранять разрешённый draft с ещё неисполняемыми предметами/талантами; ограничение симуляции остаётся прежним. Неверный вид файла, повреждённые поля или дубли ID не заменяют карточку. Максимальный размер файла —2МиБ; имена скачиваний содержат дату/время и уникальный суффикс.

Загрузка NPC заменяет только выбранного противника в **черновике состава**. В карточках показываются изменённые профили, статистика явно помечена как исходная/неактуальная, а JSON результата и его скачивание сохраняют исходный отчёт. Скачивание отдельного NPC сохраняет изменённый профиль. У заголовка состава появляется сброс черновика; загрузка исходного NPC также может снять изменения. Скачать бой изменённого состава нельзя, пока он не пересчитан; пересчёт ручного draft в этой функции не добавлен.

«Запустить генератор» по-прежнему запускает новый поиск по запросу и сбрасывает черновики. Загрузка другого полного отчёта тоже сбрасывает их; ошибочный файл отчёта сохраняет открытый draft. Смена партии сохраняет draft, отдельно помечая старый отчёт устаревшим. Во время расчёта действия с профилями заблокированы; поздняя загрузка не перекрывает новый Run или изменившуюся карточку. Черновики хранятся только в открытой вкладке — скачивайте нужные NPC до закрытия/нового поиска. [Граница и решение](../../decisions/ADR-0117-granular-character-files-and-npc-drafts.md).

## Данные персонажей

Названия книжных характеристик (Characteristics), навыков (Skills) и предметов показываются с оригиналом или устоявшимся сокращением в скобках (например WS, BS), например «Сила (Strength)» и «Щит (Shield)». Числовые поля заполняют колонки: на широком экране четыре в строке, на узком число колонок подбирается по ширине без обрезания подписей, dropdown имеет отступ стрелки от края, поле характеристики (Characteristic) зелья усиления (Enhancement Potion) выровнено с колонкой предмета. Место под полосу прокрутки зарезервировано: карточки и JSON не сдвигают страницу по горизонтали. Идентификаторы JSON не переводятся.

Визуальной группы «Партия игроков» нет: игроки отображаются отдельными карточками, под ними — кнопка добавления игрока. Характеристики (Characteristics) подписаны WS/BS/S/T/I/Ag/Re/Fel, навыки (Skills) подписаны полными оригинальными названиями. Полные названия характеристик доступны в подсказках и доступных подписях. Содержимое party в JSON сохраняет прежние идентификаторы.

Текущий dynamic JSON1 принимает факты, без внутренних настроек исполнителя:

```json
{
  "actor_id": "герой",
  "characteristics": {"weapon_skill": 3, "strength": 3, "toughness": 3, "agility": 3},
  "skills": {"melee": 5, "defence": 5, "athletics": 4, "endurance": 4},
  "equipment": {
    "weapons": [{"id": "sword:1", "weapon": "sword", "location": "right_hand"}],
    "armour": [
      {"id": "body:1", "kind": "light_armour", "location": "worn"},
      {"id": "helmet:1", "kind": "helmet", "location": "worn"},
      {"id": "shield:1", "kind": "shield", "location": "left_hand"}
    ]
  },
  "consumables": [],
  "talents": ["lucky"],
  "resources": {"fate": 3}
}
```

Это элемент party, а не самостоятельный запрос; полные примеры — [автоматический UI](ui.request.json) и [малый CLI с явными ограничениями](search.request.json). Каждая запись equipment — отдельный экземпляр с уникальным id. Location задаёт начальное положение: оружие в руке/обеих руках либо carried (убрано); броня/обычный шлем worn либо carried; щит в руке либо carried. Body armour и щит учитываются отдельно; обычному шлему не придан дополнительный бонус поверх комплекта. Щит разрешает Defence против Shooting. Для2H выбирается both_hands; конфликт рук не исправляется молча. Поддержан прежний2H→carried1H backup. Общий dual wield/смена инвентаря ещё не реализованы. Добавление оформлено компактной нейтральной кнопкой «Добавить» без иконки, размер88×36, с белым фоном и лёгкой серой рамкой; контекст действия остаётся в подсказке и aria-label; удаление — нейтральные кнопки с крестиком в таком же стиле, подсказкой и aria-label. Внутри тегов крестик и кнопка меньше, чем у предметов; отдельной кнопки добавления таланта нет. У файловых кнопок, переключателей вида и остальных действий есть синие hover/active-состояния; disabled не подсвечивается. В покое добавление/удаление нейтральны, при hover получают мягкий зелёный/красный акцент соответственно. Основной Run сохраняет приоритет. Цвет дублируется иконками/текстом, текстовый контраст проверен по [WCAG](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html); визуальный вес локальных действий выбран с учётом [GOV.UK Buttons](https://design-system.service.gov.uk/components/button/).

Расходники показаны плоским списком с лёгкими разделителями, без вложенных рамок и подзаголовков. Сверху у каждого одинаковая строка предмет/количество/крестик, ниже — только нужные параметры и короткое описание. Количество обозначает запас предметов и не меняет силу одного применения. Разные эффекты не сдвигают quantity и не смешиваются с соседними предметами.

Расходники редактируются в отдельной группе: например `{"id":"potion:1","kind":"healing_potion","quantity":2,"characteristic":null}`. Для enhancement_potion characteristic обязателен (например strength). Судьба расположена рядом с именем персонажа. Таланты можно вводить и удалять тегами; подсказки открываются под полем, сразу добавляют тег по клику или Enter; поддерживают навигацию стрелками и закрытие Escape. Собственный талант добавляется через предложение в том же списке. Подключены Lucky, Wizard, Defensive Stance и Wild Attack; прочие отмечаются как неподдержанные.

Инвентарь с двумя мечами в руках и глефой carried или другими талантами можно описать и скачать без потери данных. Но расчёт с ещё не реализованными effects/actions отклоняется **до симуляций** с явной причиной. Для рабочего расчёта нужны поддержанный loadout и исполнимые расходники (либо пустой consumables). Это разделение описания и исполнения, а не игнорирование неучтённых предметов. [Текущая граница](../../decisions/ADR-0115-inventory-draft-and-talent-tags.md).

Генератор поддерживает смешанные Melee/Shooting составы; ниже описан общий ranged-компонент и его текущая Close-граница.

Сцена явно начинает новую сессию: Fate доступен полностью, персонажи здоровы. В melee против Minions PC автоматически выбирают Attack/цель, standard Recover себе/союзнику или Help конкретному Test по текущему состоянию; задавать получателей вручную не нужно. Это ограниченная оценка ближайшего действия без дополнительных Monte Carlo-прогонов, а не оптимальный ИИ. NPC выбирают Shoot/Reload по фактической готовности; melee NPC сохраняют Attack-тактику. Fate: Glorious при0начальных успехов и полезном перебросе, Near Miss при результате раны≥11; ресурсы списываются фактически. Оба вида зелий подключены по [ADR-0119](../../decisions/ADR-0119-pc-potions-in-dynamic-encounters.md); первая магия подключена по [ADR-0120](../../decisions/ADR-0120-pc-elemental-magic-in-dynamic-encounters.md). [Границы автоматической тактики](../../decisions/ADR-0118-automatic-pc-melee-tactics.md).

Имена скачиваемых JSON запроса, результата и повтора боя получают UTC дату/время с миллисекундами и короткий уникальный суффикс, например `encounter-request_2026-11-15T20-15-30-123Z_a1b2c3d4.json`. Повторные скачивания не используют одно и то же имя. Это имя файла, оно не меняет seed или данные расчёта.

## Стрельба персонажей

[Полный запрос](pc-ranged.request.json) задаёт стрелка с Многозарядным пистолетом (Repeater Pistol), Щитом (Shield) и запасным Мечом (Sword), а также обычного бойца ближнего боя. Пример содержит лишь четыре симуляции для проверки запуска; для оценки баланса используйте автоматический план UI или увеличьте число trials.

Если тяжёлые раны (Wounds) не оставили автоматическому стрелку пригодных рук, он выполняет стандартное Восстановление (Recover), а бой партии продолжается. Руки, оружие и раны от этого не восстанавливаются; проверки Critically Injured сохраняются. При одной пригодной руке по-прежнему возможен законный переход на запасное оружие. [Принятая тактика](../../decisions/ADR-0130-automatic-pc-recover-with-no-usable-hands.md).

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/pc-ranged.request.json
```

Поддержаны также Пистолет (Pistol) и Многозарядный ручной арбалет (Repeater Handbow). В карточке игрока выберите начальное оружие; заполните Меткость (Ballistic Skill; BS), Инициативу (Initiative; I), Стрельбу (Shooting) и Ловкость рук (Dexterity). В `party[].ranged` подтвердите начальный заряд и запас боеприпасов; для двух пистолетов нужны ещё Знание (Lore: Blackpowder) и набор (Blackpowder Kit), у Handbow эти два поля равны `null`. Факты не выводятся из других характеристик. При выборе начального melee-оружия необязательные стрелковые факты сохраняются в редактируемом описании, но не используются в расчёте.

Optional запасное оружие — один carried одноручный предмет из текущих шести melee-видов; при двух оружиях нужна Сила (Strength)≥2. Щит (Shield), броня, зелья, поддержанные таланты и магия задаются прежними фактами. Генератор автоматически выбирает стрельбу, режим Repeater, Перезарядку (Reload), помощь (Help), обратимую смену и другие доступные действия. Начальное оружие не обязывает стрелять первым действием. Заряд и прогресс перезарядки сохраняются после смены; выпавшее оружие поднимается действием Восстановления (Recover).

В отчёте `pc_ranged_counts` хранит каждого стрелка в исходном порядке, включая нули: `shots`, `bonus_shots`, `shooting_help_tests`, `bonus_help_tests`, `reload_actions`, `weapon_swaps`. Помощь Стрельбе (Shooting Help) не считается выстрелом. Применённый бонус Repeater требует перезарядки и после Help, даже если проверка не дала успехов. Смена оружия не добавляет основное действие. Native replay сохраняет конкретные item IDs/positions и `automatic_combat`; Help использует `target:"attack"` с `skill:"melee"|"shooting"`, а помощь защите — тот же `skill` при отдельном target. Старые `automatic_melee`/`melee_attack`/Help `protection_skill` не принимаются.

Граница — текущая неподвижная all-Close сцена против Minions. Два пистолета в руках, несколько запасных оружий, другие дальности и полный инвентарь книги пока не исполняются. Ограниченный прогноз до трёх действий не является оптимальным планированием всего боя. [Решение и приёмка](../../decisions/ADR-0125-pc-automatic-close-shooting-and-weapon-switching.md).

## Снаряжение динамических NPC

Автоматические диапазоны включают Staff, Dagger, Axe, Sword, Warhammer, Morning Star, три описанных ниже ranged weapons, Light Armour и Shield для melee NPC. Генератор сам выбирает компоненты и их комбинации; ручной `search_space` может ограничить их. Каждое оружие одноручное; Shield занимает другую руку и пока разрешён только melee NPC. Два оружия одновременно и Heavy Armour пока не выдаются. Навык Defence варьируется отдельно от Melee/Athletics; Damage и Resilience вычисляются, а не задаются готовым statblock.

Свойства исполняются в реальном бою: Axe получает+1Damage против armoured цели, Sword даёт+1d Defence при отсутствии Staggered, Warhammer получает+1d Melee против Staggered цели, Morning Star наносит S+1Damage и получает−1d Melee при собственном Staggered. Drained удаляет положительные кубы, но не Damage bonus Axe. Shield добавляет+1Resilience отдельно от Light Armour. Печатные conceal/terrain свойства Dagger/Staff не дают бонуса к обычной боевой проверке.

Перед каждым противопоставлением NPC автоматически выбирает Defence (WS) либо Athletics (Ag) по ожидаемым успехам после реальных modifiers и cap; при равенстве — Defence. Поэтому выбор может меняться после Staggered/Drained, а не закрепляется случайным полем во входе. Это ограниченная тактика, не гарантия оптимума по всем исходам. Generated NPC пока не стреляют.

В JSON компонента NPC и ручном `search_space` обязательны `defence` и `shield`; текущие примеры мигрированы без compatibility-веток. При `search_space:null` всё выводится автоматически. В native replay сохраняются полный `generated_components`, основная `protection` и `alternate_protection`; без компонентов лишний профиль не допускается. Отдельный NPC-файл включает Defence/Shield, карточки показывают навык, предметы и их свойства в tooltip.

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/equipment.request.json
```

[Пример](equipment.request.json) выполняет4Monte Carlo-боя и допускает четыре новых оружия со Shield либо без него. Малый запуск проверяет путь, а не репрезентативность баланса; он не обязан выбрать все разрешённые предметы. Для реального поиска используйте автоматический план UI или свою точность. [Контракт](../../decisions/ADR-0121-generated-npc-melee-equipment-and-protection.md).

## Стрельба динамических NPC

Генератор сам выбирает Пистолет (Pistol), Многозарядный пистолет (Repeater Pistol) и Многозарядный ручной арбалет (Repeater Handbow) наряду с melee-оружием. Стрелковые характеристики и навыки независимы от готовых статблоков. В ручном `search_space` доступны `ballistic_skill`, `shooting`, `initiative`, `dexterity` и новые значения `weapon`; диапазоны этих полей применяются к стрелкам. Без ручных ограничений используются факты партии, где известны; для нынешней melee-партии fallback — BS/I2–4 и Shooting/Dexterity3–5. Это область поиска, не предел книги.

Результат, отдельный NPC-файл и скачанный replay сохраняют полный `ranged` component: BS/Shooting/I/Dexterity, loaded/ammunition и firearm Lore/Kit. У melee NPC `ranged:null`. Стрелок начинает без Shield, со свободной второй рукой для Reload; Light Armour разрешена. Сочетание ranged weapon+Shield не исправляется автоматически. Сгенерированные NPC могут иметь одинаковое оружие и разные параметры; именной reserve не нужен.

Pistol исполняет повторные Shoot→Reload3→Shoot, причём успехи Reload набираются настоящими Dexterity Tests. У repeaters программа сама сравнивает обычный выстрел и бонусный залп с будущей ценой Reload. Обычный shot не открывает новый Reload; залп открывает, даже при MISS. Решение не требует пользовательского паттерна или дополнительного Monte Carlo. В статистике состава отдельно показаны средние NPC shots/bonus shots/Reload actions; это наблюдения фактических действий.

Игроки автоматически выбирают законную защиту против Close Shooting: Athletics, Melee либо Defence с работающим Shield. Прежние Fate/Lucky, Help, руки/раны, зелья и два Elementalism spell продолжают действовать. Сцена пока stationary all-Close: луки, другие дальности, движение, NPC Shield+Reload и backup стрелка сюда не включены.

[Пример смешанного пула](ranged.request.json), четыре smoke-симуляции:

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/ranged.request.json
```

Выборка мала и демонстрирует интерфейс, не точность баланса. [Принятая граница](../../decisions/ADR-0124-generated-npc-close-shooting-and-reload.md). Native PC JSON1 использует `scenario.enemies[].ranged`; прежний ключ `pistol` удалён без compatibility-ветки. Текущие M61–M63 примеры мигрированы на тот же owner.

## Таланты динамических NPC

Генератор выбирает совместимые поднаборы трёх книжных талантов (Talents), не привязанных к имени NPC:

- Сопротивление магии (Magic Resistance): каждое затрагивающее cast spell получает−1Potency для этой цели; при0 эффект не исполняется. Для Lightning Blast уменьшается Damage; Fire Breath сохраняет исходный предел числа целей и свой фиксированный Damage при положительной target Potency. Miscast не блокируется.
- Оборонительная стойка (Defensive Stance): WS≥3. При собственном Staggered и успешной Defence против Melee NPC снимает своё состояние вместо действительно доступного нового Staggered атакующему.0v0, Athletics и уже Staggered атакующий обмена не дают.
- Дикая атака (Wild Attack): S≥4. Свежий NPC перед Melee получает Staggered и делает следующую проверку Glorious с перебросом доступных провалов. При Drained/Staggered тактика не применяет талант. Цена учитывается Sword/Morning Star до броска; дополнительного действия/Fate нет.

Drained не отключает пассивные Magic Resistance и Defensive Stance. Требования проверяются по текущим исходным характеристикам NPC; повторных покупок/ranks у этих талантов нет. XP history и исключение бесплатного Character Creation в этом генерируемом наборе не моделируются.

В ручном `search_space.allowed_talents` указывайте разрешённый пул, например `["magic_resistance", "defensive_stance", "wild_attack"]`. `[]` отключает таланты. Перечислять все сочетания не нужно: программа сама выбирает допустимый поднабор. `search_space:null` разрешает все три автоматически. Мутации не сохраняют талант с нарушенными Requirements; невалидный загружаемый NPC отклоняется, не исправляется удалением таланта.

Выбранные `npc.talents` сохраняются в отчёте, отдельном NPC-файле и полном `generated_components` скачанного боя. В карточках показаны настоящие теги с подсказками; разрешённый пул редактируется в прежних необязательных ограничениях NPC. Для PC Defensive Stance/Wild Attack подключены отдельно; произвольные player tags не превращаются в исполнимый эффект.

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/talents.request.json
```

[Пример](talents.request.json) выполняет4боя, seed42, при WS3–5/S4–5. Это smoke-проверка, не репрезентативная оценка. Генератор не обязан выбрать каждый разрешённый талант. Текущие JSON1 требуют `allowed_talents` в ручном пространстве и `talents` в компонентах NPC; старые текущие примеры мигрированы, compatibility decoder отсутствует. [Принятое решение](../../decisions/ADR-0122-generated-npc-combat-talents.md).

## Боевые таланты игроков

В `party[].talents` доступны Оборонительная стойка (Defensive Stance) и Дикая атака (Wild Attack). Обычные требования — WS≥3 и S≥4 соответственно. Если Talent бесплатно получен при создании (Character Creation), укажите `"talent_acquisition":{"wild_attack":"creation_free"}`; без записи используется `earned` с проверкой требований. Это факт персонажа, а не настройка поведения. В UI отметка доступна у выбранного тега; скачивание одного игрока и боя сохраняет её.

Тактика сама решает, выгоден ли Wild Attack перед атакой (Attack) либо помощью в ближнем бою (Melee Help), с учётом Fate и риска Staggered. После оплаты выбранное действие и цель сохраняются. Defensive Stance меняет новый Staggered атакующему на снятие собственного только при фактической успешной Defence; ongoing Condition от раны15 снять так нельзя. Новых ручных policy во входе партии нет. Магическая устойчивость (Magic Resistance) у PC пока не подключена: generated NPC не колдуют.

[Пример](pc-talents.request.json) содержит обычное приобретение и бесплатный Talent с невыполненным порогом S. Проверка запуска на4симуляциях:

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/pc-talents.request.json
```

Это smoke-пример с малой точностью, не репрезентативная оценка баланса. Граница и правила: [ADR-0123](../../decisions/ADR-0123-pc-combat-talents-and-committed-melee-intent.md).

## Применение зелий

В `consumables` доступны Healing Potion и Enhancement Potion для WS/Strength/Toughness/Agility. `quantity` — конечное число полных порций; partial doses не моделируются. Другие четыре Characteristics можно сохранить в draft, но расчёт до их реализации блокируется. Автоматическая тактика выбирает момент применения; здоровый персонаж не обязан пить лечебное, а усиление без будущей пользы может остаться в запасе. Каждая Characteristic добровольно усиливается не более одного раза за бой, даже при нескольких одинаковых предметах.

Питьё занимает Recover с одной пригодной рукой без отдельного сброса. Healing восстанавливает собственную рану текущего боя и связанные эффекты, включая Defenceless; выпавшее оружие одновременно не подбирается. Чужие Conditions не исчезают. Начальный запас восстанавливается независимо для каждого Monte Carlo-боя; исходный JSON не изменяется.

Статистика состава показывает средний расход за бой. В JSON `potion_use_counts` содержит фактические суммарные расходы каждой пары actor/item по всем trials, включая нули; делите count на trials для среднего. Поле отсутствует при отсутствии начального запаса. Исполняемый replay сохраняет инвентарь и повторяет применение/расход.

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/potions.request.json
```

Это небольшой пример на4боя для проверки пути, не репрезентативная оценка баланса. Для реального поиска используйте автоматический план UI либо задайте точность вручную.

## Магия персонажей

Добавьте талант Маг (Wizard) в карточке игрока. Появятся Разум (Reason/Re), Воля (Willpower), происхождение (Origin), уровень мага (Wizard Level1–4), запомненные заклинания (Memorised Spells) и магические принадлежности (Arcane Paraphernalia). Текущая школа — Elementalism; доступны Lightning Blast и Fire Breath. Снаряжение и зелья остаются в прежних редакторах. В UI и JSON вводятся факты персонажа; момент Casting, выбор заклинания и целей определяет симулятор.

В элементе `party` добавляются `characteristics.reason`, `skills.willpower`, тег `wizard` и блок:

```json
"magic": {
  "origin": "human",
  "wizard_level": 4,
  "lores": ["elementalism"],
  "memorised_spells": ["lightning_blast", "fire_breath"],
  "arcane_paraphernalia": true
}
```

Это фрагмент персонажа; [полный запрос](elemental-mage.request.json) исполняется командой:

```powershell

.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/elemental-mage.request.json
```

Пример содержит всего4Monte Carlo-боя для проверки запуска. Уровень4 выбран для меньшего риска Miscast, а не как требование CV2: оба заклинания разрешены уже на уровне1. Dwarf/Halfling не допускают Wizard по книге; отсутствующая Lore/kit, неверный ранг или неподдержанные spells блокируются до Monte Carlo. Броня (Armour), включая надетый шлем (Helmet), и используемый щит (Shield) делают Casting мрачным (Grim). По согласованной трактовке нужна одна пригодная рука, которую не требуется отдельно освобождать от оружия; здоровая приоритетна, травмированная вызывает настоящий Critical.

Маг использует настоящий Exacting Willpower Test: успехи накапливаются, сила (Potency) берётся из последнего броска, девятки нельзя перебросить. Lightning Blast наносит4+Potency Damage, по бронированному —5+Potency; Fire Breath поражает доPotency разных врагов, по3Damage или4без брони. Это прямой урон без Attack/Protection Test. Обычный Recover уменьшает Miscast Pool; прерывание активной попытки даёт свой куб. Эффекты Miscast обязательны и после победного заклинания.

Первая сцена явно дневная, все участники в Close одной Zone, без выхода; NPC — обычные numeric/generated Minions. В скачанном native replay сохраняются полный профиль `wizard` и `facts.daylight_confirmed=true`. Поддержаны боевые строки Miscast1–4/7–16/19–22/25–32/35–36/39+. Результаты5–6/17–18/23–24/33–34/37–38 требуют предметного/пространственного/GM-продолжения: сохраняются настоящий roll и точный `UNSUPPORTED_PATH`. Это не пропущенный эффект. Любой observed unsupported исключает состав из рекомендаций, поэтому `selected` может быть пустым; увеличение trials повышает шанс обнаружить эту границу. Общая магия всей книги и исчерпывающее покрытие Miscasts пока не заявляются.

В статистике UI показаны средние Casting/spells/Miscasts/неподдержанные Miscasts за бой. JSON `magic_counts` содержит суммарные целые `casting_actions`, `spell_casts`, `miscasts`, `unsupported_miscasts` для каждого мага в исходном порядке, включая нули. Эффекты заклинания и Miscast не считаются дополнительными действиями. При отсутствии магов поле отсутствует. Начальные накопления/пулы и запас предметов независимы в каждом trial; replay сохраняет факты и воспроизводит расходы. Автоматические диапазоны NPC учитывают Lightning Blast, ручные ограничения не заменяются. [Принятое решение](../../decisions/ADR-0120-pc-elemental-magic-in-dynamic-encounters.md).

## Seed и воспроизводимость

Повторяемость предполагает одинаковую реализацию тактики: обновление алгоритма может изменить бой и результат поиска с прежним seed. Актуальный executable replay сохраняет `automatic_combat`; полный Python-результат боя даёт причины выбора в `tactical_decisions` без нового прогона.

Seed задаётся явно в форме или JSON. Он не меняется при запуске/отмене, а переключатель нового seed удалён. Одинаковый seed и полный запрос воспроизводят поиск и его результат; другое значение можно ввести вручную. Фактический seed хранится строкой uint64 в source/report без потери точности. UUID отдельного HTTP-запуска служит только для адресной отмены и не участвует в RNG/отчёте.

## Прогресс генерации

После запуска виден краткий статус без полного журнала:

- Создаём состав N из M.
- Предварительная оценка: сколько симуляций состава завершено, сколько побед и текущий процент.
- Независимая проверка финалистов; её counters начинаются заново для каждого состава.
- Завершение: фактическое число симуляций и процент побед рекомендованного состава по итоговой проверке; при отсутствии подходящих составов процент не придумывается.

Обновление — примерно раз в секунду. Последняя оценка сохраняется при переходе к следующему составу, история сообщений не накапливается. Проценты до завершения предварительные, не гарантия сложности. Индикатор считает завершённые симуляции; он не предсказывает оставшееся время. Поиск может закончиться раньше верхней границы плана, например при маленьком пространстве комбинаций. После отмены остаётся последний известный общий count, без частичного итогового отчёта.

Временная потеря связи со status endpoint не останавливает расчёт. Старые ответы не меняют новую генерацию; смена запроса по-прежнему не запускает Run автоматически. Прогресс не меняет RNG/seed или итоговый JSON.

## Отмена генерации

После запуска кнопка «Запустить генератор» на том же месте заменяется красной «Отменить генерацию». После завершения/отмены возвращается запуск; во время подтверждения отмены кнопка показывает «Отмена…». Она посылает серверу команду остановки именно текущего HTTP-запуска. Интерфейс показывает «Отмена…» и ждёт фактического завершения; редактирование разблокируется после подтверждения. Это не только прерывание browser fetch: поиск проверяет сигнал перед кандидатами/возвратом, а стандартный simulator — перед бросками. Остановка кооперативная, на ближайшей контрольной точке. Завершённые до отмены части не выдаются как полный результат; скачивание результата недоступно. Можно сразу запустить расчёт заново с тем же seed.

Запоздавшая отмена другого запуска отклоняется. Ранняя отмена, пришедшая до регистрации generation POST, запоминается для его token (ограниченное множество128записей); новый запуск использует другой UUID. Если расчёт уже завершён, интерфейс получает его завершённый результат. CLI JSON families не имеют нового отменённого report: это UI transport control. Python search/execute допускают optional cancel_requested callback; для внешнего custom simulator checkpoint гарантируется между его вызовами, для стандартного — также внутри dice RNG.

Числа точности рассчитываются по партии, допустимым компонентам и стоимости симуляций; фиксированного800-trial профиля больше нет. Автоплан ориентируется на750s работы, сохраняя отдельную независимую проверку финалистов. Seed42из файла используется до ручного изменения. Загруженный файл/--request включает ручной план и сохраняет четыре управляющих числа; бюджет всё равно выводится автоматически. Короткий search.request.json остаётся самостоятельным12-trial smoke-примером для CLI и тестов. [Решение](../../decisions/ADR-0126-cost-aware-search-planning-and-decision-reuse.md).

Одна модель стоимости обслуживает и автоплан, и оценку времени. Она учитывает численность, цели/предел раундов, активные характеристики, стрельбу и магию, запасное оружие/Щит (Shield), таланты (Talents) и компоненты NPC. В проверенных примерах при1–10NPC получились планы404/194/174trials для melee/mixed/magic партий; это не универсальные defaults. [Модель и калибровка](../../benchmarks/dynamic-planning-2026-11-17.md). Два полных mixed/magic плана исполнены без уменьшения выборок; [время, точность и ограничения](../../benchmarks/dynamic-full-auto-plan-2026-11-17.md).

Кандидаты увеличивают разнообразие поиска; предварительные бои дают грубый отсев, а новые бои финалиста уточняют его вероятность победы. При observed50% интервал Уилсона95% для64боёв ≈38–62%,128боёв ≈41,5–58,5%,256боёв ≈43,9–56,1%,400боёв ≈45,1–54,9%. Расчёт по [формуле NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm). Интервалы относятся к фиксированному составу/тактике, не доказывают полноту пространства поиска, надёжность порядка финалистов или точность среднего числа раундов. Фактическая validation ограничена доступным временем и может быть меньше256; для точности около±5п.п. задайте finalist_trials около400 вручную, учитывая стоимость.

## JSON/CLI

Запуск JSON/CLI из корня репозитория:

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m towr generate-encounter docs/examples/dynamic/search.request.json > generated.json
```

После установки доступна та же команда `towr generate-encounter INPUT`; `-` читает UTF-8 JSON из stdin. [Полный входной пример](search.request.json) содержит party/scene, число NPC, цели, настройки поиска и необязательное пространство компонентов. Нет enemy reserve, target_priority или defeat_decisions в партии. Эти поля создаются при сборке найденных боёв; порядок партии определяет PC activation/NPC target priority, порядок NPC — PC target priority/NPC activation. `defeat_disposition` явно подтверждает общее GM-решение для созданных целей.

«Возможные параметры противников» — единая группа ручных ограничений генерации внутри необязательного раздела. Она объединяет параметры, снаряжение и способности (Abilities); новые группы добавляются при появлении самостоятельных настроек, без заранее пустых разделов.

JSON family `dynamic_encounter_search`, version1: `search_space` можно опустить или передать null: сервер построит диапазоны вокруг партии. Explicit объект задаёт массив разрешённых значений каждого параметра и массив альтернативных наборов abilities, ограничивая поиск по желанию пользователя. `npc_count.minimum/maximum` ограничивают численность. `targets.win_rate` и `targets.started_rounds` — сокращённые дроби `{numerator, denominator}`; например3/5 и3/1. Только integer JSON tokens, seed — десятичная строка uint64. Бюджет обязан покрывать `max_candidates * exploration_trials + top_k * finalist_trials`. Все поля закрыты; неподдержанные компоненты/режимы и несогласованные значения отвергаются до симуляции.

### Совместные цели и статус результата

Генератор одновременно приближает обе цели: долю побед с допуском±10процентных пунктов и среднее число начатых раундов (Rounds) с допуском±1. При целях50%/5это40–60%и4–6; границы включены. Допуски фиксированы согласованным контрактом, новых полей ввода нет. Ранжирование сначала уменьшает худшую ошибку в единицах допуска, затем сумму таких ошибок. Идеальное совпадение вероятности с плохой длительностью больше не получает автоматический приоритет.

Текущий JSON1 результата содержит `target_criteria` с `basis="point_estimates"`, `win_rate_tolerance=0.1`, `started_rounds_tolerance=1`; у каждого состава — `target_assessment`. Его status принимает `within_targets` (обе оценки в допуске), `outside_targets` (приближение вне хотя бы одной полосы) либо `unsupported`. `target_match_found` относится только к поддержанным финалистам после независимой validation. `selected` сохраняет лучшие поддержанные варианты и при отсутствии совпадения; UI явно сообщает об этом.

Это совпадение точечных оценок выборки, не95%сертификат и не гарантия будущих боёв. Длительность сохраняет прежнюю метрику started rounds, включая остановленные префиксы; round-limit не считается победой, actual unsupported не квалифицируется даже при численном совпадении осей. Интервалы оценки по-прежнему показываются отдельно. Изменённый запрос/NPC draft не пересчитывает старую статистику.

Python: `result.target_match_found` и `assess_dynamic_candidate(result.source, candidate)` из `towr.application.dynamic_encounter`. Metadata вычисляются из источника/агрегатов при кодировании и проверяются при импорте. Старый result JSONбез этих полей нужно пересчитать из его `source_request`; отдельного compatibility-формата нет. [Решение и точные границы](../../decisions/ADR-0137-joint-encounter-targets.md).

### Параллельное исполнение

`execution` принимает `{"mode":"sequential"}` либо `{"mode":"process","workers":4}`. Workers — целое1–61; sequential не принимает workers, публичного batch_size нет. Один pool обслуживает все составы поиска, параллельно исполняются независимые бои одного состава. При одинаковых входе, seed и плане фактические результаты совпадают; порядок промежуточного завершения боёв может отличаться.

Новый запрос UI автоматически использует до четырёх процессов, оставляя один логический CPU свободным; на машинах с одним/двумя CPU используется sequential. Загруженный запрос сохраняет свой execution. Режим можно изменить в JSON. Автоплан и оценка времени учитывают измеренное ускорение и запуск pool; это не линейное деление на число процессов. При изменении автоплана меняется выборка, поэтому результат уже может отличаться.

Прогресс считает завершённые и проверенные бои. Отмена кооперативно останавливает выполняющиеся workers, освобождает pool и лишь затем подтверждает завершение; следующий запуск получает новый сигнал отмены. Ошибки workers возвращаются как ошибки исполнения, без скрытого перехода на sequential или частичного успешного отчёта. [Контракт и проверки](../../decisions/ADR-0129-dynamic-process-execution.md).

Пример ограничен3кандидатами ×2trials +2финалистами ×3trials =12trials максимум. Для полезной оценки увеличьте trials и budget: например12×16+3×64=384. Значения smoke-примера демонстрируют формат и воспроизводимость, но дают широкие интервалы.

Поиск использует случайные перезапуски и мутации перспективных составов. Часть адаптивных проб добавляет одного NPC, если оценка побед игроков выше цели, либо удаляет одного, если ниже; остальные параметры сохраняются. Границы, точное попадание и unsupported не вызывают принудительного шага в обратную сторону. Случайные перезапуски сохраняют весь диапазон, но полный охват при малом бюджете не гарантирован. Равномерные начальные пробы отклонены; [принятая стратегия и ограничения](../../decisions/ADR-0128-directed-count-proposals.md), [замеры](../../benchmarks/dynamic-planning-2026-11-17.md#направленные-пробы-численности). При переменной численности тот же seed после обновления алгоритма может дать другие составы; текущий поиск воспроизводим, фиксированное число/один кандидат сохраняют прежний путь. Поля JSON и ручные настройки прежние.

JSON-результат содержит `source_request` (полный точный вход), `resolved_search_space` (фактически использованные диапазоны), `explored`, отдельные `validations`, `selected` (ID только финалистов без observed unsupported), фактические `total_trials`, `proposal_attempts` и `proposal_limit_reached`. Каждый кандидат содержит NPC компоненты, win rate/Wilson95, mean started rounds/Hoeffding95, outcome counts и `replay` — полноценный текущий PC simulation JSON1. Чтобы повторить конкретный бой:

```powershell
$r = Get-Content generated.json -Raw | ConvertFrom-Json
$r.validations[0].replay | ConvertTo-Json -Depth 100 | Set-Content replay.json -Encoding utf8NoBOM
.venv/Scripts/python.exe -m towr simulate-pc-melee replay.json
```

Команды записи рассчитаны на PowerShell7. Ошибки входа дают JSON `dynamic_encounter_search_error` и exit2; сбой исполнения — exit3 без частичного результата; ошибки I/O — exit4. Диагностика идёт в stderr. Схемы [request](../../../src/towr/adapters/schemas/dynamic-encounter-request-v1.schema.json), [result](../../../src/towr/adapters/schemas/dynamic-encounter-result-v1.schema.json), [error](../../../src/towr/adapters/schemas/dynamic-encounter-error-v1.schema.json) разрешаются offline.

Authored Drained-on-hit допускается только явной альтернативой `search_space.abilities: [[], ["drained_on_hit"]]`; по умолчанию `[[]]`. Это разрешённый авторский компонент, не автоматическая выдача книжного таланта. Действующий owner учитывает фактическое попадание и независимый источник Conditions.

Это лучшие найденные приближения к совместным целям при заданной тактике и бюджете. Точечное совпадение с обоими допусками явно отмечается, глобальный оптимум не гарантируется. Длительность включает цензурированные round-limit/unsupported префиксы. Если наблюдался unsupported, такой screening кандидат не проходит в validation; unsupported validation сохраняется в отчёте, но не в selected. Пустой selected — допустимый честный результат.

Python API: `towr.application.dynamic_encounter.DynamicEncounterRequest`, `NpcSearchSpace`, `search_dynamic_encounter`. По умолчанию используется sequential aggregate. Для process передайте `execution=SimulationExecutionOptions(mode=SimulationExecutionMode.PROCESS, workers=4, batch_size=1)` из `towr.application.ranged_simulation_models`; вызов из standalone script защитите `if __name__ == '__main__'`. Custom simulator можно передать отдельно, одновременно с execution он не допускается. Предыдущий [Python-пример](search.py) также работает: он переиспользует партию из M10, отбрасывая прежних enemies. Новый JSON-вход полностью самостоятельный и такого scenario не требует. Расширять нужно составляемые компоненты и их prerequisites, а не список именных statblocks.

### Управляемая выборка числовых параметров

Python API `NpcSearchSpace.resample_numeric` создаёт новый числовой вариант всего состава, сохраняя его снаряжение (Equipment), таланты (Talents) и способности (Abilities). Пример из корня репозитория:

```python
from pathlib import Path
from random import Random
from towr.adapters.dynamic_encounter_json import parse_dynamic_encounter_request

request = parse_dynamic_encounter_request(
    Path('docs/examples/dynamic/search.request.json').read_text(encoding='utf-8')
).request
rng = Random(606)
template = tuple(request.space.sample(rng) for _ in range(request.maximum_npcs))
sample = request.space.resample_numeric(template, Random(707), bias=0.5)
scenario = request.scenario(sample.composition, 'controlled')
print(sample.variable_fields, sample.changed_members)
```

`bias` от−1до1смещает веса к меньшим/большим допустимым значениям;0даёт равномерную повторную выборку, а не сохранение исходных чисел. Требования талантов сохраняются. Это не вероятность победы: оценку даёт отдельная Monte Carlo-симуляция `scenario`. Metadata отражают доступную числовую свободу/фактически изменённых NPC. Штатный генератор/UI пока не вызывает этот метод: простая feedback-интеграция не прошла проверку качества. [Контракт, контроль и ограничения](../../decisions/ADR-0135-controlled-numeric-composition-sampling.md).

### Границы автоплана

Автоплан — ограниченная UI-эвристика, не дополнительное игровое правило. Ёмкость16–4096trials выводится из оценки стоимости и ориентира750s. Около50–60%отводится предварительному поиску, до64кандидатов, с8–12боями на состав. Когда12боёв не оставляют места для хотя бы8кандидатов, используются8; конечное маленькое пространство дополнительно ограничивает ширину. Остаток отводится до2независимым финалистам; желаемая точность64–256 зависит от p(1−p), но сокращается при недостатке бюджета. Фактический план виден перед запуском, ручной режим позволяет увеличить точность. Это не покрытие всех сочетаний и не жёсткий10–15мин timeout.

Оценка времени использует ту же стоимость одного боя, умноженную на фактический план. Показан широкий ориентир0.4–2.0×, округлённый в секунды/минуты/часы; это не статистический доверительный интервал, ETA прогресса или гарантия времени. Одинаковая цель по времени может давать похожий диапазон при разных партиях, но число trials будет различаться. Неполный поиск/unsupported может завершиться раньше. Недостающие характеристики не заменяются выдуманными значениями: карточки/JSON/черновики остаются доступны, запуск требует допустимого источника. Расчёт оценки не запускает MC и не меняет seed.
