# ADR-0141 — все таланты (Talents) и общий источник приобретения

Статус: **принято пользователем2026-11-19; реализация начата**. Приняты A/B/C3, Feigned Flight раз за раунд (C1) и взаимная нейтрализация противоположных tie-preferences с обычным книжным tie-break (C2). Область: все59общих талантов (Talents), PC/союзники/NPC с книжными ограничениями. Это одна предметная веха; подготовка каталога не означает её завершения.

## Источники и полный перечень

Player’s Guide1.4: III73–81 — весь реестр59,66 — XP при завершении создания персонажа (Character Creation),89 — социальные ступени (Status): Brass/Silver/Gold; V109 — равенства,111–112 — судьба (Fate),116–119 — действия, натиск (Charge) и отступление (Give Ground); VII138–149 — вера (Faith); VIII155–160 — сотворение (Casting), магическая ошибка (Miscast), импровизированные заклинания (Improvised Spells). Нормативная версия Gamemaster’s Guide —1.1; его применимые опасности/порча (Hazards/Corruption) подключаются по конкретным источникам, без переопределения Player’s Guide.

Основной нормативный реестр — [правила талантов](../rules/talents.md), перечень зависимостей и границ — [матрица всех59](../implementation-coverage.md#полная-матрица-талантов). В книге по страницам73–81 соответственно7/7/3/8/4/5/10/7/8строк. Вспомогательный [доменный каталог](../../src/towr/domain/talent_catalog.py) хранит все названия/страницы/базовые XP/Requirements, виды приобретения и необходимые выборы; он **не расширяет battle admission** и не заменяет исполнение эффекта.

Старые решения сохраняются: Defensive Stance заменяет только фактически доступный новый Staggered; Wild Attack фиксирует действие/цель до цены; Creation Free не придумывается при недостаточной характеристике. Новых именованных NPC-пресетов не требуется.

## A. Принятый единый публичный источник

1. Один типизированный источник приобретённых талантов у всех участников. Отдельные `EncounterTalent`, `GeneratedTalent`, теги, `has_lucky`, Wizard Level и combat-talent facts перестают быть независимыми истинами. Финансирование Fate остаётся ресурсом PC; наличие таланта не выдаёт NPC Fate. UI показывает прежние теги, а параметры раскрываются только у требующих их талантов.
2. В актуальном Dynamic/PC JSON1 `talents` становится списком объектов: `id` и непустой `acquisitions`. Каждое приобретение хранит `phase: creation|advancement`, `funding: free|xp`; `free` допустим только при `creation`. Выбор, если нужен этой покупке, хранится в её собственном typed `choice`. Дубликаты singleton-талантов запрещены. Схемы, character files, native replay, UI, примеры и тесты мигрируют вместе, без второй версии/compatibility-ветки.
3. Бесплатное приобретение при создании снимает **перечисленные Requirements**, но не отменяет текстовые условия использования, завершённый поиск Грааля (Grail Quest), несовместимость Faith с колдовством или физическую необходимость книги/инструмента. `creation + xp` — отдельный законный путь; нельзя ошибочно запретить его трём creation-only талантам.
4. Wizard: максимум4покупки. Familiar: каждая покупка даёт другой эффект из девяти; это не напечатанная шкала уровней1–9. Faith: один бог, покупки1/2 дают Favour/Prayers, с3-й каждая добавляет **одно** Miracle. Уже использованные Miracle задаются конечным начальным ресурсом, не обнуляются на trial/session. История GM-подтверждения преданности относится к соответствующей покупке.
5. Общие базовые факты персонажа включают восемь характеристик (Characteristics), необходимые навыки (Skills), происхождение (Origin), знания (Lores), социальную ступень (Status) и предметы (Equipment). Необходимый отсутствующий факт нельзя получать из выдуманного default. Дополнительные поля обязательны по фактически выбранным возможностям; отсутствие неиспользуемого навыка не становится compatibility-веткой. Повреждения/временные бонусы не переоценивают законность давнего приобретения.
6. Выбранная группа Hatred — семантическая группа происхождения/фракции/региона, а не список actor IDs. Динамические NPC получают соответствующие факты; генератор строит допустимые комбинации и зависимости, не берёт готовые statblocks. Расовые/социальные ограничения и несовместимости проверяются до Monte Carlo. Автопул не выдаёт произвольную магию, клятву, бога или GM-подтверждение из отсутствующих данных: пользователь разрешает соответствующие семейства/факты в search space.
7. Решения Attack/Help/Recover/Manoeuvre, реакции, цели и расход ресурсов остаются автоматическими по действительному состоянию и ограниченной общей оценке пользы/риска. Пользователь не вводит внутренние ledgers, заранее выбранные actor-пары или последовательности тактики. Непосредственно наблюдаемые нарушения Strictures/vows исполняются; сюжетная оценка GM не подменяется случайным числом.

Внутри текущих result families1 добавлены наблюдения `rapid_reload_counts` и `npc_aim_counts`: только реально исполненные дополнительные действия и Aim с полным источником; source-ordered нулевые строки обязательны для соответствующих владельцев. Они отделены от Bear/Crown/Fate counters. У запроса нет новых tactical полей Rapid Reload; общий источник приобретения определяет право, автоматический исполнитель — выбор. Это не новая wire version и не compatibility-ветка.

Пример формы источника, без рангов, вычисляемых повторно из отдельного поля:

```json
{
  "talents": [
    {
      "id": "wild_attack",
      "acquisitions": [{"phase": "creation", "funding": "free"}]
    },
    {
      "id": "hatred",
      "acquisitions": [{
        "phase": "advancement",
        "funding": "xp",
        "choice": {"group_id": "orcs"}
      }]
    }
  ]
}
```

Это не полноценный Character Creation/XP-оптимизатор. Декларируется законный начальный боец и конечные ресурсы; стоимость хранится для проверки происхождения и будущего развития.

## B. Реакции, действия и однократность — принято

Нужны небольшие явные владельцы событий и typed receipts, не универсальная шина событий/язык правил.

- Bash Attack, Interceptor и Stand and Shoot получают отдельное разрешение немедленной атаки, с полным trigger/source/weapon/target. Оно не изображается обычным дополнительным Standard slot и не расходует обычное действие следующего хода. Полные ограничения атаки, руки, заряд, условия и последствия сохраняются. Эта интерпретация PG73/77/80 относительно PG116 подтверждена пользователем.
- Для обычных действий сохраняются максимум2и запрет повтора. Fight As One даёт явное исключение третьего действия только при напечатанном сочетании способности маунта и его другого оружия. Fate/Rapid Reload/Quick Throw/оружие не складываются в произвольное третье действие.
- Сначала фиксируются фактические Test/Attack results. Defensive Stance заменяет обычное ещё не исполненное miss-Staggered, затем завершается выбранное обычное последствие. Riposte разрешается после этого, если его владелец жив и источник всё ещё допустим. Это принятый пользователем порядок там, где книга не задаёт полного порядка. Он не изменяет принятую трактовку Defensive Stance и исключает повторное использование одного trigger.
- Остальные одновременные реакции одного окна рассматриваются в стабильном порядке активации source; после каждой заново проверяются живые участники, дистанции и возможность действия. Stand and Shoot завершается до соответствующего движения/атаки Charge; Interceptor — по фактическому Give Ground, Bash Attack — только по действительно наложенному Staggered. Нельзя отложить все эти реакции до конца хода.
- Once/round/session/battle/downtime — отдельные runtime receipts. Предварительная оценка тактики не бросает RNG и не расходует ресурс. Повторное чтение native proof не накладывает эффект второй раз.

## C. Принятые решения по неоднозначности

### C1. Feigned Flight: turn или round

PG76 пишет «once per turn, as normal», PG119 — «once per round». **Пользователь выбрал:** общий предел одного Give Ground за раунд для всех источников, включая этот Talent. Отдельное исключение раз за ход не принято. Это явная трактовка расхождения, не подтверждённая errata.

### C2. Противоположные преимущества равенства

Два участника с Short Size при Opposed Strength поPG80 одновременно отдают победу своему оппоненту. Возможны столкновения с Battlefield Musician и другими источниками. **Пользователь выбрал:** противоположные специальные преимущества взаимно нейтрализуются; применяется обычный книжный tie-break для данного Test. Одностороннее преимущество сохраняется. Ничья0v0 остаётся двумя провалами поPG109. Порядок элементов JSON не определяет победителя. Это явная пользовательская конкретизация конфликта, не напечатанное общее правило.

### C3. Присутствие фамильяра (Familiar)

PG75 не задаёт дальность слова nearby у Armoured; Linked разрешает уход, Skulker — исчезновение, а Combatant не содержит явной дальности. **Принятый контракт:** состояние фамильяра хранит жив/уничтожен и manifested/linked-away/hidden, а `nearby_confirmed` — явный факт GM, без выдуманного универсального расстояния. Факты начальной сцены задают, находится ли он рядом и участвует ли физически в бою. Armoured требует подтверждённой близости; Bookrest — действительного удержания гримуара; Combatant — подтверждённого участия в бою. Уничтоженный фамильяр не предоставляет ни один эффект. Для дальних/скрытых состояний отдельно сохраняются напечатанные сенсорные и магические возможности; глобального правила «всё работает из другого измерения» нет. Это GM-конкретизация, её нужно принять вместе с контрактом A/B, а не молча принять в коде.

### C4. Благосклонность Ранальда (Ranald’s Favour): округление — принято

PG146 делит рейтинг опасности падения (Hazard) пополам, не задавая округление. PG73 отдельно говорит округлять вниз до0 только для Акробата (Acrobatic); это не автоматическое общее правило. Пользователь2026-11-19 подтвердил округление вниз, минимум0 (5→2). Это явная пользовательская трактовка неуказанного округления; вариант вверх не выбран. Она будет применяться при интеграции Faith; принятие решения не объявляет этот runtime готовым.

### C5. Пробой брони (Armour Bane) и метеоритное железо — принято

PG73 требует оружие с бонусом урона против брони либо игнорированием брони; GM85 Armour of Meteoric Iron отменяет такие mundane effects. Не указано, достаточно ли исходного свойства для отдельного снижения Resilience талантом. Пользователь подтвердил: квалификация только по фактически действующему свойству; отменённый немагический источник не запускает Armour Bane. Вариант отдельного обхода ward не выбран. В Dual Wield происхождение каждого contributor проверяется отдельно: магический основной предмет не делает обычный Axe магическим.

Полный перечень qualifying modes из Equipment: Axe/Halberd/Greataxe (PG93), Crossbow/Pistol/Handgun/Hochland Long Rifle/Repeater Pistol/Repeater Handgun (PG95), Throwing Axe (PG96), Ogre Pistol (GM103):11. Именованные Magic Weapons сами по себе не наследуют эти Traits. Один успешный Attack даёт одно снижение независимо от количества qualifying contributors. Сначала сохраняется действительный Damage/Wound result прежнего Resilience; Near Miss не отменяет HIT и повторный Staggered не создаёт ещё одно снижение.

### C6. Срок и носитель снижения Resilience от Armour Bane — принято

PG73 снижает Resilience цели на1, минимум её Toughness, без выбора повреждённого предмета/repair/reset. Пользователь подтвердил для текущего боя: actor-owned сумма **фактически применённых** снижений, не damage конкретного предмета. Она сохраняется при drop/pickup/swap/dismount/remount и лечении, применяется к актуальным бонусам с clamp до текущего Toughness; новый trial начинает с исходного бойца. Срабатывание при нулевом бонусе не создаёт скрытый долг на будущие предметы, но фиксирует снятие armoured при Resilience≤T по специальному правилу PG73. Физические предметы, вес, Traits, Helmet и Meteoric ward не уничтожаются.

Вариант отдельного GM-решения при смене защиты не выбран. Это явная пользовательская трактовка неуказанного lifecycle, а не подтверждённая errata. Повторно C5/C6 не спрашивать.

### C7. Братья по оружию (Allies in Arms): момент снятия состояния — принято

PG73 разрешает при Помощи (Help) снять Пошатывание (Staggered) с помощника либо получателя; успех проверки не требуется. PG108/117 задаёт настоящую проверку Help, но не помещает снятие состояния до или после неё. Это существенно для штрафов оружия, цены Дикой атаки (Wild Attack) и самой проверки помощника.

Пользователь подтвердил: после окончательного результата проверки Help, включая перебросы, снять одно снимаемое Staggered у одного из этих двух участников, до будущей проверки получателя. Нулевые успехи разрешают Talent. Обычная проверка помощника сохраняет действительные Conditions на момент броска; бонусы уже сделанной проверки не пересчитываются. Постоянная причина от раны15 не снимается. Действие/получатель Help фиксируются до его цены; автоматика выбирает помощника либо получателя по пользе без нового случайного решения. Вариант снятия перед проверкой Help не выбран. Это явная пользовательская трактовка неуказанного порядка, не подтверждённая errata; повторно не спрашивать.

Проверки после выбора: PC/генерируемый NPC как helper и beneficiary, нулевой успех, self/ally и ongoing Staggered, Wild Attack/оружейные modifiers, фактический Help Test и его upcoming-Test source, однократное снятие и полный replay. Бесплатные named NPC Help abilities не подменяют обычный Help Test.

### C8. Оглушающий удар (Bash Attack) после натиска (Charge) — принято

PG73 даёт немедленную бесплатную Melee Attack после фактического Brawn→Staggered. PG117/119 связывают Charge bonus с атакой в составе Charge; отдельного порядка наследования для возникшей следом реакции нет. Это влияет также на оружейные/броневые и mounted Traits с условием «при Charge».

Пользователь подтвердил: исходная атака использует собственный действительный Charge source; последующая Bash Attack — отдельная немедленная атака без нового движения и **без наследования Charge bonus/charge-only Traits**. Актуальная верховая позиция, higher ground, outnumbering, Staggered/Prone цели и остальные обычные модификаторы сохраняются. Вариант наследования bonus/Traits не выбран. Это явная пользовательская трактовка неоговорённого взаимодействия, не подтверждённая errata. Повторно не спрашивать.

Проверки: обе стороны, настоящий Brawn Charge→новый Staggered→Bash, точная provenance и once-only; отсутствие новой movement/ordinary action, допустимые held/carried Melee items/руки, charge-only weapon/armour/mount Traits отдельно от постоянных mounted преимуществ. Trigger и отдельная immediate grant уже приняты в B и не переоткрываются. Bash-подготовка явно использует отсутствие Charge source; текущий mounted source и остальные факты сцены сохраняются.

## D. Зависимости и очередь внутри всей области

1. Общий59-каталог, приобретение/выборы/Requirements, единый source PC/NPC, schema/character/UI и проверка независимых источников Lucky/Wizard. Теги сами по себе не включают новые неподключённые эффекты.
2. Общие modifiers/conditions/Help/раны и контекст знаний: Armour Bane, Mighty Blow, Hardy, Allies in Arms, психология/иммунитеты/восприятие/Short Size и связанные источники. Модификатор от предмета отличается от штрафа раны; Minion не получает выдуманный Wounds Table.
3. Движение/отступление/реакции/маунты, Aim/Reload/Charge, лидерство/музыка, лечение/хирургия. Back in the Saddle отменяет прежний уход маунта именно при использовании этого Talent; для Steer Clear нужна также настоящая модель пассажира/управления транспортом, а не только удобный mounted-поднабор.
4. Общий caster для NPC и PC, Dispeller/ongoing spells, Familiar, Wizard/Touched и необходимые формы Casting. Недостающая возможность относится к остатку вехи, даже если одновременно приближает следующую область всей магии. Каталог всех именованных заклинаний остаётся следующей областью; настоящее разрешённое применение форм Casting, которое обещает Talent, является зависимостью текущей.
5. Faith: все10богов PG140–149, их Favour и30Prayers. Miracle — согласованное с GM конкретное вмешательство и конечный заряд; не выдумывать универсальный случайный «божественный урон». Вход хранит доступные GM-подтверждённые вмешательства; автоматика выбирает среди допустимых и применяет настоящие последствия. Пустой набор не означает фиктивную реализацию всех Miracle.
6. Контекстные/повествовательные свойства: явные Music/Insight/Scrutinise/poison/corruption и GM-сведения, где это применимо сцене. Не выдавать ложный боевой бонус за Quick Change/Secret Bloodline/Vouch For Them; не объявлять все социальные/сенсорные свойства внебоевыми только из-за отсутствующего consumer.

Каждый шаг небольшой и проверяемый; список не превращается в новые пользовательские вехи. Вся область не закрывается до обработки всех строк матрицы и зависимостей; фактический остаток хранится в статусе.

## E. Проверка

Каталог:59строк/источники/цены/Requirements,3repeatable exceptions, создание за XP отдельно от бесплатного, явные выборы Familiar/Faith/Wizard, типизация и immutable source. При дальнейшей интеграции: одинаковое правило для PC/союзника/NPC, отсутствие NPC Fate, реальные source/разовый trigger, конечный расход и запрет чужого proof; negative modifiers/Drained/ongoing Conditions; границы0v0/конфликтов/дистанций/живых целей. Для каждой связной возможности — нужные native replay/JSON/source и короткий dynamic-путь. Один representative sequential/process при изменении исполнения реакций/источника, без повторения backend-матрицы для каждой строки.

Полный regression — в контрольной точке значимого изменения общего источника/реакций и затем завершения области по фактическому риску. Wheel только при изменениях доставки/ресурсов/dependencies/entry points или перед выпуском. Новый дорогой поиск/полный автоплан505не назначается.

## Фактическая реализация подготовки

### C9. Акробат (Acrobatic) и взлёт Пегаса (Pegasus/Fly) — принято

Player’s Guide1.4, III73, Acrobatic снимает блокирование движения врагами и явно включает Give Ground. Gamemaster’s Guide1.1, VII176, Pegasus/Fly специально запрещает move/Give Ground в midair Zone, когда начало движения — Close наземного врага. Rider и mount используют общие способности по PG124; Pegasus Knights передаёт Fly подходящему всаднику. Приоритет этих двух текстов не указан.

- ВариантA (рекомендуемый): Acrobatic снимает именно enemy-only запрет взлёта/воздушного Give Ground. Действительные Fly, включённый airspace, корректные маршрут/назначение и прочие ограничения сохраняются.
- ВариантB: специальный запрет Pegasus/Fly сохраняется; сначала надо действительно выйти из Close наземного врага по земле.

Это не отмена отдельного запрета начинать Натиск (Charge) из Close и не способность летать без настоящего источника Fly. Пользователь2026-11-20 принял вариантA: Acrobatic снимает именно enemy-only запрет взлёта/воздушного Give Ground. ВариантB не выбран. Проверка после выбора: оба acquired owners PC/generated NPC; настоящий наземный enemy Close → midair move/GiveGround разрешён только по выбранному варианту; отсутствие Fly/airspace, препятствия, состояния и исчерпанные бюджеты по-прежнему блокируют, snapshot сохраняет всех врагов. ### C10. Перекрытие маршрутов врагами в динамической сцене — принято

PG1.4 V114 оставляет физическую возможность пройти внутри Zone за GM; общие Movement/Give Ground owners уже имеют точные `path_entity_ids`. Наличие врага в той же Zone само по себе не доказывает, что маршрут проходит через него: вход в занятую врагами Zone для Give Ground отдельно допустим со своим Broken. Нынешняя динамическая сцена хранит Zones/Close и не хранит микропозиции или GM-перекрытия; её native requests не могут честно выдумать `path_entity_ids`. Для полного эффекта Acrobatic нужен доступный генератору источник этого условия, общий обеим сторонам.

Пользователь2026-11-20 принял минимальный контракт: optional `scene.enemy_zone_blocking: boolean`, default `false`, и такое же поле в `PcBattlefieldSpec`/current PC JSON1. `true` — явное GM-подтверждение узких проходов: живые враги в промежуточных Zones перекрывают проход через них; враг в Close у исходной позиции перекрывает выход из этой Zone. Враг в конечной Zone сам по себе не считается пересечённым на пути. Для чистого перемещения в воздухе наземные промежуточные враги не пересекаются; фактические воздушные враги проверяются в своих Zones. Специальное правило взлёта Pegasus/Fly действует отдельно поC9. Within-Zone микромаршрут эта настройка не выдумывает. Снимок участников/близости не меняется: requests сохраняют фактические IDs живых блокирующих врагов; Acrobatic разрешает пройти именно через них. Препятствия, terrain, состояния и бюджеты остаются прежними.

Альтернатива: сразу отдельный GM-ввод перекрытий для каждого конкретного маршрута/участника, со своим контрактом валидации и поведением при переменной численности генерируемых NPC. Это точнее для сложных сцен, но существенно больше данного условия узких проходов. Ни один вариант не делает любое соседство универсальным книжным запретом.

Адресные критерии после выбора: current JSON parsing/roundtrip/default false; actual PC и generated NPC route через живого врага блокируется безAcrobatic и разрешается с ним; raw IDs остаются в receipt, смерть/уход блокирующего снимают именно его присутствие; enemy destination не стирается и сохраняет GiveGround/Broken; воздушные пути/C9; остальные obstacles/terrain/once budgets не обходятся; native replay отвергает подмену/удаление witness. Новая wire version/compatibility не нужны.

### C11. Спешенные маунты для Снова в седле (Back in the Saddle) — принято

PG1.4 III73 разрешает оставить спешенного маунта в Close и одним move/Recover встать с Prone и сесть в седло. PG124 отличает единый mounted entity без отдельного хода животного от спешенного существа со своим NPC profile под контролем GM; последнее может брать свой ход, но обычны и пассивное ожидание/уход. Нынешний `PcMountedState(mounted=False)` означает ушедший маунт; отдельной живой цели/ран/положения/возврата нет. Прежний GM departed source не отменяет новый Talent, но один bool near=true дал бы неуязвимый предмет вместо существа.

Предлагаемый общий контракт для PC и NPC: оставшийся маунт становится типизированным связанным существом своей стороны с собственными profile/Conditions/Wounds/позицией/идентификатором. Это источник боевого участника, не ветка по имени всадника. Книжные profiles служат defaults/проверками компонентов. Пока на маунте едут, сохраняются книжные single-entity targeting/ход всадника; после разъединения существо доступно настоящим атакам и Close/area/Hazard последствиям, без NPC Fate. Восстановление mounted entity не сбрасывает его предыдущее состояние; пригодность/близость/земля или реальный Fly проверяются. Stand+remount использует настоящий разрешённый free move либо Recover, с hand/Wound/end-phase и once budgets, без бесплатного дополнительного действия.

Пользователь2026-11-20 выбрал `wait_and_recover` и отдельный ход со следующего раунда после всадника. Это явная принятая GM-конкретизация; повторно не спрашивать. Альтернатива `attack_and_recover` не выбрана.

Рассмотренные условия GM и тактика:

- Рекомендуемое `scene.dismounted_mount_policy="wait_and_recover"`: животное остаётся у места спешивания, со следующего раунда получает свой слот сразу после всадника и использует self Recover при необходимости, иначе ждёт; не атакует и не даёт Help. После окончательной гибели/ухода всадника покидает поле по этой явной GM policy. Спутники учитываются отдельно от исходного `npc_count`, не превращаются в бесплатные раны/поражения всадника.
- Альтернатива `"attack_and_recover"`: такой же настоящий спутник с сохранёнными состояниями и порядком, но выбирает собственные допустимые Attack/Recover; оставшийся враждебный спутник продолжает бой и учитывается в условии очищения сцены. Это заметно расширяет автоматическую тактику и стоимость боя, но не меняет текст Talent.

В обоих вариантах optional новое scene-поле относится к GM-поведению животного, а не к ручной тактике PC. Текущая сцена без оставшегося существа сохраняет прежний departed путь. Фактическое право остаться/выбор владельца должно подтверждаться acquired Back in the Saddle или другим настоящим источником; поле не дарит Talent и не восстанавливает погибшего маунта. Регистрация отдельного участника со следующего раунда — предлагаемая явная конкретизация порядка GM, книга её не задаёт. Не объявлять этот Talent подключённым до реализации всего выбранного контракта. Самостоятельные Attack/Help спешенного маунта этим выбором не включены.

Проверки выбранного контракта: реальные PC/generated NPC dismount→retained creature→stand+remount с полным replay, родительский/creature HP не смешиваются; повторный remount не лечит/не обновляет ресурсы; уничтожение/Prone/Defenceless/удаление маунта не оставляет buffs или фиктивного pickup; hazards/nearby включают реальную новую цель; mounted single-entity targeting и shared обычный action budget сохраняются; порядок новых ходов не даёт второго слота за прежнюю mounted часть раунда; current JSON/source/character files/UI и tiny sequential/process сценарий.

### C13. Состояния маунта после remount — принято

PG124 отдаёт mounted паре характеристики/навыки/Abilities всадника с добавленными mount Abilities; отдельный wounded steed с последующим remount и прежними Conditions прямо не расписан. C11 уже требует сохранить собственные раны/состояния животного, без лечения от remount. Например, Demigryph на1–2Wounds получает Drained поGM175, и этот band не сбрасывается после посадки.

Пользователь2026-11-20 принял отдельное действие источников: Drained/Staggered животного изменяют проверки, использующие **его** профиль, а не автоматически собственную Melee/Defence всадника. Ранения/физические ограничения животного сохраняют Speed/Fly/пригодность; мёртвый/Defenceless/Prone маунт не становится исправным средством передвижения. Альтернатива — эффективное объединение Conditions обоих на все проверки mounted пары, по одному штрафу данного Condition, с сохранением исходных владельцев для дальнейшего dismount/лечения. Во всех случаях раны HP не переходят между телами, remount не создаёт свежего NPC.

Принятая конкретизация периодики: сохранённые ongoing эффекты каждого тела исполняются по его HP на end phase хода всадника, пока mounted; отдельного creature action/turn нет. Пока detached, используется собственный ход спутника поC11. Подтверждённая гибель/неспособность не должна оставлять mounted buffs; Pegasus W1 CanNotFly/следующая посадка сохраняют собственный band и используют часы фактического владельца текущей пары. Это требует явного source/clock receipt, не копирования Wounds/Conditions в injury всадника.

Проверки: Drained Demigryph после remount, same-condition обоих без двойного случайного модификатора, истечение/устранение одного источника не стирает другой, W1Pegasus не получает свежего Fly, periodic source/HP/clock однократны, повторный remount не лечит и не обновляет periodic budget.

### C15. Подъём, посадка и перемещение — принято

PG1.4 III73 позволяет Снова в седле (Back in the Saddle) встать и сесть на маунта «as part of the same move or Recover». ### C16. Обязательная посадка раненого Пегаса (Pegasus) — принято

### C17. Боевой музыкант (Battlefield Musician) — принято

Источники: PG1.4 III73 (сам Talent), III72/V107 (Лидерство, Leadership, от Обаяния, Fellowship), III82/88 и IV98–99 (торговые инструменты, Trade Tools, и Знание музыки, Music Lore), V114/116/123 (дальность, действия и Оглушение, Deafened). PG73 требует Musician’s Gear, разрешает бесплатный сигнал на собственном ходу либо отдельное Leadership-действие; каждый успех вдохновляет одного слышащего союзника в Medium. При атаках до следующего хода музыканта равенства отдаются защитнику.

Принятая полная граница для PC и генерируемых NPC, включая союзные стороны:

- Физические `equipment.tools[]` с постоянным `id`, `kind="musicians_gear"`, положением предмета и GM-фактом `hands_required=1|2`. Инструмент учитывается вместе с оружием и щитом в хвате, переноске, падении, подборе и использовании травмированных рук. Книга не назначает всем инструментам одно число рук. Описательный prerequisite-флаг сам по себе не создаёт предмет.
- Настоящие `characteristics.fellowship` и `skills.leadership`; использование инструмента требует Music Lore по общему правилу Trade Tools. Бесплатное приобретение Talent не отменяет операционное требование к инструменту. Генератор выбирает допустимые инструмент/знание/рейтинги из разрешённого пространства, сохраняя источник приобретения и проверяя prerequisites при мутации/перевыборке. UI и character files показывают эти факты.
- Бесплатные сигналы присутствия и отступления — отдельные однократные incidental receipts на своём ходу, без броска и без action slot. Они не создают автоматического Retreat/Broken у слушателей. Автоматика сообщает присутствие при начале поддержки и отступление при собственном выбранном уходе; дублирование сигнала тем же источником в тот же ход не допускается. Книжное Medium-ограничение вдохновения не переносится на сигнал; сам факт слышимости сигнала сохраняется отдельно.
- Вдохновение — настоящее оплаченное `IMPROVISE/ABILITY` с Leadership Test. Ноль успехов расходует действие. После окончательного броска выбираются разные живые союзники в Medium, способные слышать музыку; музыкант не выбирает себя. Автоматика сравнивает пользу поддержки с остальными действиями и выбирает получателей по ожидаемому снижению риска входящих атак. Нужен явный акустический факт сцены: GM подтверждает, что музыку в пределах Medium можно слышать, либо задаёт акустические преграды; одна геометрическая дистанция слышимость не доказывает. Deafened отдельно запрещает получение эффекта.
- Общий типизированный tie-source входит в фактический Attack/Protection и в ту же оценку тактики: Melee, Shooting, Throwing, Brawn, немедленные и естественные атаки, обе стороны. Проверки без Opposition не получают преимущества;0:0остаётся двумя провалами. C2 о нейтрализации противоположных предпочтений уже принят и повторного выбора не требует. Сохраняются связанные реакции, включая Defensive Stance при настоящей победе защитника.
- Источник вдохновения хранит музыканта, конкретный инструмент, окончательный Test, получателей и срок до следующего собственного TurnStart. Не заменять этот срок концом раунда и не создавать фиктивный ход умершего музыканта.

Пользователь2026-11-20 принял полный контракт и обе рекомендованные трактовки: дальность/слышимость проверяются при получении; последующее движение, тишина или Deafened не стирают уже полученное вдохновение. При гибели/уходе музыканта эффект сохраняется до следующего фактического хода этого музыканта; если такого хода больше нет, до конца боя. Альтернативы — постоянное требование слышимости и досрочное снятие при смерти/уходе — не выбраны. PG73 отдельно эти случаи не определяет; принятые конкретизации не выдавать за официальную errata и повторно не спрашивать.

Consumer подключён; фактические проверки и точка продолжения находятся в [статусе](../project-status.md). Критерии адресной приёмки: настоящий предмет/хват/ранившаяся рука/drop/pickup, строгие Lore и приобретения, PC/NPC действия/сигналы,0/несколько успехов и distinct beneficiaries, фактические Medium/hearing/Deafened, граница следующих своих часов и исчезновение музыканта, общий tie/0:0/cancellation/Defensive Stance, совпадение advice и исполнения, replay/однократность, текущие JSON/schema/UI и малый sequential/process путь.

Реализация использует отдельный типизированный инвентарь инструментов, совместно проверяемый с руками оружия/щита. Весь текущий physical bank восстанавливается из исходных предметов и точных квитанций подготовки/подбора/выпадения; стёртый или повторный переход отвергается. По PG92 инструменты — снаряжение (Trappings), а не дополнительные Weapons в числовом лимите Strength; произвольный вес/громоздкость по числу рук не выводятся.

`scene.music_acoustics={audible_confirmed,blocked_zone_pairs}` задаёт условия GM. Относительные ключи `zone:0`/`air:0` сохраняются между составами поиска, но разрешаются в настоящей геометрии каждого боя; неизвестная Zone отвергается. Пары описывают слышимость между зонами, а не выдуманную симуляцию распространения звука. При null автоматика не использует музыку. `leadership` и `musician_instrument_hands` входят в ограничения генератора; физический предмет и Music Lore не создаются из prerequisite-флага. Оценка поддержки ограничена текущими подготовленными проверками/рисками, не обещает оптимальной тактики всего боя.

Текущие результаты сохраняют `music_counts`: действия, платные подборы, вдохновлённые союзники, сигналы и защищённые положительные ничьи. Одна реальная атака считается не более одного раза у каждого музыканта, даже при нескольких его действующих источниках. Действия и подборы включены в прежний общий бюджет, сигналы не получают action slot. Прежние форматы не сохранялись отдельными compatibility-ветвями.

### C18. Благословения Леди (Blessings of the Lady): окно молитвы — принято

Следующий consumer внутри общей области59талантов (Talents), не новая сокращённая веха. Источники: PG1.4 III74 (Blessings of the Lady), III77 (Honour Bound, Code Chivalric/Rules of Knightly Honour), V112 (Near Miss). Нужны полный источник обета, prerequisites и применение для PC/применимых NPC; NPC не получает Fate. Проверка GM исполнения обета не должна выводиться из произвольной строки `oath_id`.

PG74 разрешает молитву «in the first turn of a battle» либо непосредственно перед боем. Текст не уточняет, означает ли это первый собственный ход каждого участника или единственный первый ход всего боя. **Пользователь выбрал первый собственный фактический ход каждого бойца.** Это явная трактовка, не подтверждённая errata; повторно не спрашивать.

Принятая граница: любой допустимый обычный action slot первого собственного фактического хода. После завершения этого хода окно не переносится на следующий. NPC второй стороны сохраняет своё окно после ходов PC; участник, впервые реально получивший ход позднее первого раунда (Round), проверяется по своей истории, а не по `round_number == 1`. Молитва перед боем требует отдельного явного GM-условия и действительно совершённого действия, а не бесплатного скрытого setup. Альтернатива единственного первого хода всего боя отклонена.

Подготовлены отдельные проверяемые механизмы: `LadyPrayerActionRequest/Result` расходует настоящий ordinary slot и сохраняет полный prefix TurnStart; `LadyBlessingState` хранит молитвы, единственный расход за бой и потери; `LadyWoundNegationRequest/Result` отменяет одну настоящую рану до её последствий без расхода Судьбы (Fate). Поддержаны обычная/фиксированная рана персонажа и рана профиля NPC, без преобразования Minion/Brute/Monstrosity в персонажа. Прежние раны и Пошатывание (Staggered) сохраняются при полной отмене; дополнительные неотменённые раны остаются. Повторная молитва не восстанавливает израсходованную отмену. Сломленность (Broken) не создаёт запрета до искупления; нарушение обета создаёт, а подтверждённое GM искупление само по себе не возвращает утраченное благословение.

Это ещё не native consumer: фактический владелец обязан связать полный prefix часов, настоящее pending Wound, приобретённый Talent и GM-факты. Honour Bound, автоматическая тактика, replay/journal, текущий JSON/UI и генерация остаются продолжением; runtime cap не открыт. Адресные проверки — `test_lady_blessing_resource`, `test_lady_prayer_action`, `test_lady_wound_negation`; ближайшие зависимости — injury/lifecycle/Fate Near Miss. Полный regression/wheel для этого независимого внутреннего шага не требуются.

### C19. Обет (Oath) и контекст сцены для Honour Bound/Lady — принято

Согласованный A6/A7 запрещает выводить содержание обета из произвольной строки `oath_id` и заставлять пользователя задавать последовательность тактики. Для полного подключения Благословений Леди (Blessings of the Lady) и Связанного честью (Honour Bound), PG74/77, **Пользователь подтвердил** следующий текущий Dynamic/PC JSON1-контракт без compatibility-ветки:

- Необязательный `oath_context` у владельца обета: при наличии Honour Bound его `oath_id` совпадает с `OathChoice`, `gm_confirmation_id` — источник решения GM, `in_good_standing_confirmed` — соблюдение на начало сцены. Контекст не выдаёт сам Talent и не обходит Requirements. Бесплатное приобретение Lady при создании может законно обойти prerequisite Honour Bound: в этом случае подтверждается соблюдение vows/code для благословения, но не придумывается право активировать отсутствующий Honour Bound.
- `combat_tests_fulfil_oath_confirmed`: явное подтверждение GM, что боевые проверки этого участника в данной сцене служат его обету. При false Honour Bound не применяется к ним; успех и нарушение не придумываются по имени обета. В true-контекст входят фактические Attack/Protection/Help и проверки действий текущего боя, а не весь последующий campaign/session.
- `forbidden_attack_skills` — закрытый список Melee/Brawn/Shooting/Throwing и `fleeing_breaks_oath` — явно подтверждённое содержание конкретного обета. Это факты GM, не универсальное переопределение книжного Кодекса (Code Chivalric). Автоматика исключает запрещённые намерения; действительный вынужденный поступок получает соответствующее последствие. Повествовательные нарушения/искупление передаются явным исходным GM-статусом, не случайным событием.
- `lady_prayer_before_battle_confirmed` подтверждает действительно совершённое действие непосредственно перед этим боем. По умолчанию false: без подтверждения автоматика рассматривает настоящую платную молитву в первом собственном ходу (C18). Предварительная молитва не занимает action slot внутри боя и не появляется из одного тега.
- Ресурс активации Honour Bound — один раз за session; для свежей сессии свободен, при продолжении задаётся подтверждённый исходный расход. Автоматика выбирает Glorious либо трату Fate на Unmitigated Success; тратится session pool/первый Lucky spend, рейтинг Fate не сжигается. NPC доступен только Glorious и не получает Fate. Обычные ограничения реального Unmitigated Success сохраняются; числовой бросок не подменяется придуманным количеством успехов.
- Ограничения генератора получают явно разрешённые сочетания полного Talent/OathChoice/контекста GM; без таких данных автопул не создаёт произвольный обет, его исполнение или предварительную молитву. UI показывает эти исходные факты рядом с соответствующим Talent; внутренние ledgers/action sequences не становятся полями формы.

Публичный допуск откроется только вместе с prayer/negation, Honour Bound, наблюдаемым нарушением, автоматическими решениями, native replay и PC/generated NPC вводом. Проверки: обе стороны и C18 clocks; реальные ordinary/Fate slots; once/battle против once/session; запреты/искупление; полные Wound sources без двойной регистрации и побочных последствий; сохранение ресурсов при переключении действий; JSON/schema/UI и малый сквозной поиск. Process parity — один репрезентативный случай изменения механизма, без полной матрицы и большого Monte Carlo-прогона.

C19 **принято пользователем2026-11-20**; повторно не согласовывать эти исходные GM-факты. Реальные эффекты, ресурсы, текущий ввод и генерация подключены вместе с C20; общий runtime cap открыт после native/public проверок.

### C20. Unmitigated Success: числовые исходы автоматического боя — принято

При подключении альтернативы Honour Bound выявлена отдельная граница, которой C19 не определяет. PG1.4 V111 гарантирует Полный успех (Total Success), разрешает согласовать исключительный исход с GM и требует реалистической достижимости. Но PG108 прямо отличает базовые проверки (Basic Tests) от атаки (Attack), помощи (Help) и длительных проверок (Exacting Tests), где используется количество успехов. Подтверждение «бой служит обету» не является подтверждением произвольного числа успехов. Нельзя заменить реальный0вTrace на3или придумать максимальную награду молча.

Предлагается один явный GM-допуск `unmitigated_success_scope_confirmed` в контексте C19 (по умолчанию false), означающий следующий ограниченный сценарный порядок. Это согласование способа автоматического определения исключительного исхода, а не утверждение, что книга напечатала такой числовой алгоритм:

- Исходные кубы, перебросы и реальный `TestResult` сохраняются. Отдельный типизированный outcome receipt указывает обычный исход, согласованную награду, фактический Test/контекст и настоящий расход Fate; не производится фиктивный burn или фиктивный бросок.
- Для Basic Test — Total Success. Для Attack — попадание с наиболее выгодным обычным эффектом, физически достижимым при законном максимуме успехов подготовленной атаки; максимум одна рана (Wound) одной цели. Специальные эффекты сети (Weighted Net), безоружного боя (Unarmed), огня и взрыва не превращаются в произвольную дополнительную рану. Для реально разрешённой защиты (Protection) — отражение данной атаки; отсутствие самой проверки при Defenceless/Unaware не обходится.
- Для Exacting/Reload — отдельная награда прогресса текущего объявленного Test: законный максимум его подготовленного пула с действующими success modifiers, не «3успеха» по названию Total Success и не бесплатное завершение нескольких действий. Для Help — так же ограниченный отдельный бонус данного фактического Help. Сохраняются prerequisites, руки, предметы, адресат и ограничения получения помощи.
- Для Casting — тот же отдельный прогресс/допустимая Potency текущей попытки; ограничения одного поражённого/одной Wound от Unmitigated Success сохраняются. Для Hazard — наилучшее достижимое уменьшение опасности текущей проверкой. Реальные побочные эффекты выпавших кубов, включая9и Miscast, не стираются: меняется исход Test, а не история броска или отдельная цена действия.
- Автоматика сравнивает пользу этого исхода с Glorious и стоимостью конечного Fate; за один Talent activation выбирается один путь. NPC Fate не получают. При отсутствии подтверждённого exceptional scope автоматика вправе использовать только Glorious; ресурс не расходуется на недопущенный результат.

Альтернатива: пока выбрать для автоматического боя только Glorious, сохранив отдельный low-level Unmitigated Success с явным GM-соглашением для ручного интегратора. Это уменьшает автоматическую область C19 и должно быть явно выбрано пользователем; полный native consumer Honour Bound тогда не объявляется завершённым.

C20 **принято пользователем2026-11-20**: автоматический максимум по указанному GM-допуску. C18/C19/C20 повторно не согласовывать. Подключены оба таланта для PC и генерируемых NPC; приёмочные native/JSON/spawn проверки используют штатный допуск.

Исполнение сохраняет `TestResult.successes` и Trace как фактические кубы. Отдельный проверяемый grant задаёт `effective_successes`; при сотворении (Casting) реальные9по-прежнему вызывают магические осечки (Miscasts). Оба режима Honour Bound используют один канонический банк once/session; молитвы и отмены Lady — отдельный once/battle ресурс. Банк восстанавливается из полного источника и принятых квитанций журнала, а не из предъявленного конечного состояния.

Автоматический выбор режима — ограниченная эвристика: точные распределения текущего пула сравнивают прирост ожидаемых успехов от Glorious с исправлением провала и ценой конечного Fate. Lucky учитывает реальную бесплатную первую трату. Цена в эвристике не является книжной ценой или обещанием оптимальной тактики. Если другой источник уже даёт Glorious, талант сохраняется. Для Oil/Blast/Blunderbuss автоматика выбирает Glorious: неподтверждённый предел одной Wound не оплачивается исключительным исходом, а обычные реальные площадные эффекты сохраняются полностью. Магический exceptional grant ограничивает поражение одной целью; отдельные Miscasts и цены действия сохраняются.

План приёмки выполнен адресно: чистые правила/ресурсы и provenance; native PC/NPC с полным replay; numeric Attack/Protection/Help/Reload/Casting/Hazard; реальные9, Lucky, отрицательные GM-предпосылки, подмена/сброс банка; current source/result JSON, UI и один sequential/spawn boundary. Фактические результаты — в [статусе](../project-status.md); полный regression/wheel не требуются автоматически.
