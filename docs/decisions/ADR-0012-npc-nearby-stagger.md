# ADR-0012: вторичные Staggered-цели Blunderbuss в NPC roster

Статус: принято, 2026-09-28.

## Основание

Непосредственно перечитаны BOOK-PLAYER-GUIDE 1.4, Equipment / Ranged Weapons / Blunderbuss, стр. 95; Rules / Giving Ground, стр. 119; Conditions / Staggered, стр. 123; BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91. Попадание Blunderbuss вызывает Staggered у других существ в Close Range от основной цели, без дополнительной Attack/Damage каждому. Первое/повторное Staggered и Minion Wound уже исполняет K1. Этот срез переносит готовые вторичные результаты в M2 roster; полного подключения оружия к M2 runner ещё нет.

## Контракт

`NpcNearbyStaggerExecutionRequest(state, resolution)` содержит точный NpcRosterAttackState и полный NearbyTargetsStaggerResolutionRequest. Проверяет canonical BLUNDERBUSS_NEARBY_STAGGER_RULE_ID, наличие основной цели в roster, каждый secondary actor ID, Minion policy и точное исходное injury. Уже defeated вторичные цели и дополнительные injury/effect options отклоняются как неподдержанные. Основная цель может быть defeated после исходного попадания. K1 request проверяет отсутствие основной/повторных целей и уникальные impact IDs. Сторона не фильтрует friendly fire; источник основной атаки/attacker не выбирает список автоматически.

`execute_npc_nearby_stagger(request, rng, *, decisions=None)` вызывает существующий resolve_nearby_targets_stagger ровно один раз; порядок целей, RNG и decisions передаются ему. Staggered/Give Ground/Prone/Wound не реализуются повторно. Для поддержанных Minion вариантов RNG не расходуется; repeated Staggered требует внешнего решения, кроме единственной разрешённой Wound-ветви. Ошибка оставляет вход неизменным, но внешние эффекты decision callback не откатывает.

K1 `NearbyTargetsStaggerResolutionResult` теперь требует `source_request`: resolver сохраняет полный исполненный request. Конструктор проверяет typed impacts, request/source/rule IDs, порядок и точные target/impact IDs, нормализует tuples. Одних ID недостаточно для M2: `NpcNearbyStaggerExecutionResult(source_request, resolution)` требует равенство полного resolution.source_request, включая injury и флаги Give Ground. Это изменение контракта K1; прямое ручное создание результата теперь также требует source_request. Результаты resolver по-прежнему содержат все прежние поля.

Result `.state` — immutable проекция новых Conditions/Wounds только выбранных Minions. Определения, оборудование, Resilience, порядок roster и невыбранные участники сохранены. Перенос не вызывает condition/wound resolver повторно. `.resolution` хранит все результаты и вложенную трассировку; `.applied_rule_ids` — исходная batch trace. `.pending_targets` сохраняет только NearbyTargetStaggerResult с непустыми impact.follow_ups, в исходном порядке. Target ID, impact ID и полный impact остаются вместе: два одинаковых ProfileStateChangeRequest не объединяются и не превращаются в анонимную общую очередь. Полный request с первичной целью и контекстом доступен через source_request.

`NpcRosterAttackState.consumed_nearby_stagger_sources` — ordered unique tuple из NearbyTargetsStaggerRequest (primary resolution ID + rule ID). Это отдельная история эффекта, не новая Attack/receipt и не подмножество consumed Attack IDs: первичный K1 resolution пока приходит извне. `apply_npc_nearby_stagger(current, result)` требует точный roster и все histories, отклоняет уже consumed source и возвращает result.state. Новые batch/impact IDs, изменённый состав целей или пустой список не обходят запись исходного эффекта. Пустой исходный batch допустим и тоже регистрируется. Existing Attack/Give Ground/defeat transitions используют replace и сохраняют новую историю; проверена следующая обычная Attack. Полный откат caller-owned snapshots не предотвращается.

## Границы

Это adapter supplied secondary request, а не доказательство первичного попадания или полноты Close Range списка. Caller отвечает за истинность source, полный список и его порядок, can-leave/once-per-round факты, передачу primary injury/receipt и сохранение primary pending. Одна Zone не означает Close Range. Результат не выполняет движение, не подтверждает defeat и не гасит primary NearbyTargetsStaggerRequest в NpcRoundRequest. Caller сохраняет returned state **и** полный result с pending_targets.

Обычные M2 request/controller/executor по-прежнему отклоняют secondary_effects/UNSUPPORTED_EFFECTS. Их guards нельзя снимать до полной связки primary execution, secondary batch и целевых consumers. Brute/Champion, произвольные эффекты, spatial discovery, общий AoE, runner journal integration и battle aggregate не добавлены. При встрече неподдержанного secondary target нужно отклонить этот сценарий, а не молча исключить существо из списка. Подтверждение формы поражения secondary Minion и вторичный Give Ground реализованы отдельными контрактами ниже.

## Вторичный Give Ground

Реализован 2026-09-28. Источник: BOOK-PLAYER-GUIDE 1.4, Rules / Giving Ground, стр. 119. `NpcNearbyGiveGroundExecutionRequest(id, current, spatial_state, batch, target_id, movement, previous=None)` и `NpcNearbyGiveGroundConsumptionRequest` из domain/npc_nearby_give_ground_models.py принимают соответственно pending movement request и завершённый movement result. Оба требуют полный primary-bound batch. Target-scoped GiveGroundRequest проверяется вместе с исходным Stagger choice, Conditions, actor первичной атаки, номером раунда, сторонами roster/spatial и once-per-round availability. Standalone batch без primary result не подходит. Первое движение требует exact post-batch roster/history, расширенного только подтверждениями defeat этого batch.

`execute_npc_nearby_give_ground` в rules/npc_nearby_give_ground_resolution.py выполняет один existing resolve_give_ground после preflight, проверяет возвращённый full source и вызывает один consumer. Запрещённый путь/направление отклоняет прежний spatial resolver; ошибки не регистрируются и не изменяют вход. `consume_npc_nearby_give_ground` переносит только готовые Conditions. `apply_npc_nearby_give_ground(current, spatial_state, result)` проверяет оба точных исходных snapshot и возвращает `(result.state, result.spatial_state)`. Нет повторных Attack/Stagger/Wound/Condition reducers, RNG или receipt. Placement и usage берутся из готового movement result.

`NpcNearbyGiveGroundKey(source effect, target_id)` и ordered unique `NpcRosterAttackState.consumed_nearby_give_ground` обеспечивают однократность независимо от новых batch/impact/consumer IDs. Source уже должен присутствовать в consumed_nearby_stagger_sources; остальные histories сохраняются. Result `.pending_targets` сохраняет полные исходные impacts и порядок, исключая подтверждённые defeat и исполненные Give Ground. Primary pending остаются у caller.

Для следующей Give Ground цели того же batch caller передаёт полный предыдущий consumption result в `previous`: batch, roster/history и spatial должны точно продолжать его результат. Это позволяет исполнить несколько движений в любом порядке без хранения spatial aggregate в roster. Caller сохраняет оба returned snapshot и полные results. Полный откат caller-owned snapshots не предотвращается.

Без continuation действуют прежние узкие контракты: подтверждения defeat, затем последовательные движения. При передаче явной цепочки continuation оба вида последствий теперь можно чередовать в любом порядке; подробности ниже. Книжное ограничение порядка не вводится. Автоматического поиска Close Range, исполнения primary pending и подключения к M2 runner нет; ordinary M2 secondary guards сохранены.

10 unit tests в [test_m2_npc_nearby_give_ground.py](../../tests/unit/test_m2_npc_nearby_give_ground.py) и расширенная [интеграция](../../tests/integration/test_m2_blunderbuss_secondary_roster.py): safe/enemy/already Broken, once-per-round, illegal route, stale/foreign/replay, типы/immutable/source proof, история до batch, два движения в обоих порядках и смешанный batch после defeat acknowledgement (три dispositions × две spatial ветви). Полный набор: 1673 tests OK на Python 3.14.

## Подтверждение secondary Minion defeat

Уточнение 2026-09-28. Непосредственно перечитаны BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91; BOOK-PLAYER-GUIDE 1.4, Equipment / Ranged Weapons / Blunderbuss, стр. 95. Нового игрового правила нет: attacker/GM выбирают одну из трёх существующих dispositions.

NpcNearbyStaggerExecutionRequest получил optional `primary_attack: RangedWeaponAttackExecutionResult`. При наличии он проверяется **до secondary resolver**: Blunderbuss, HIT, именованный NearbyTargetsStaggerSpec в исходном kernel request, единственный matching trigger в primary follow-ups, одинаковые primary resolution/target IDs, регистрация primary execution ID в pre-batch истории и точное post-primary injury. Проверяются actor/target и их стороны в roster/исходном round, source Attack ID/impact spec и Test/Protection IDs. Full primary result/source, receipt и reload transition сохраняются в batch source. Прежний standalone batch без primary остаётся допустимым; подтверждать defeat через него нельзя. Истинность supplied фактов, полнота Close Range списка и полный откат snapshots по-прежнему не доказываются этим локальным контрактом.

`NpcNearbyDefeatAcknowledgementRequest(id, current, batch, decision)` в domain/npc_nearby_defeat_models.py требует полный связанный batch, текущий NpcRosterAttackState и прежний MinionDefeatDecision. Target ID берётся из decision, attacker должен совпадать с сохранённым primary actor, gm_approved обязан быть True. Цель должна получить новую Minion Wound с согласованным ProfileWoundResult и ровно одним соответствующим ProfileStateChangeRequest. Defeated flag сам по себе недостаточен. Основная цель, неизвестная, живая или Give Ground цель не подходит. Friendly fire допустим; прежний MinionDefeatDecision требует разных attacker/target IDs, поэтому подтверждение собственного поражения атакующего этим контрактом не поддержано.

`NpcNearbyDefeatKey(source, target_id)` и `NpcRosterAttackState.acknowledged_nearby_defeats` хранят ordered unique keys. Source — NearbyTargetsStaggerRequest (primary resolution ID + rule ID), а не изменяемые caller batch/impact/ack IDs. Каждая запись требует уже consumed_nearby_stagger_sources. Exact post-batch roster и все истории обязаны совпадать; единственное допустимое расширение относительно batch.state — ключи ранее подтверждённых новых defeat этого же batch. Старый prefix нельзя удалить/переставить. Это позволяет подтверждать две цели в любом порядке. Для подтверждения после движения требуется полный continuation chain, описанный ниже; произвольные изменения roster по-прежнему отклоняются. Решения/dispositions сохраняет caller в отдельных полных acknowledgement results; IDs истории не заменяют эти решения.

`acknowledge_npc_nearby_defeat` и `apply_npc_nearby_defeat(current, result)` в rules/npc_nearby_defeat_resolution.py не принимают RNG и не вызывают injury/Attack/movement. Result `.state` дополняет ровно один key; `.pending_targets` — view исходных batch pending за вычетом уже подтверждённых целей. Остальные записи, в том числе Give Ground, сохраняют исходный порядок и полные impacts. Два одинаковых анонимных ProfileStateChange разделяются target IDs. Сам batch и primary pending не меняются. Consumer требует exact current source; replay с новым ack ID/disposition, повторной передачей исходных pending или переименованным batch/impact отклоняется. Caller сохраняет returned state и последний result для актуального pending view.

8 новых unit tests: обе очередности × независимые dispositions двух целей, prior-history prefix, GM/actor/target/type/source guards, missing/foreign primary, malformed Wound proof, stale/replay, неизменяемость. Existing K1→roster integration подтверждает вторичную Wound всеми тремя dispositions, сохраняя Give Ground другой цели, primary Wound pending, единственный kernel/secondary resolver и 8 RNG основной атаки. Полный набор: 1663 tests OK на Python 3.14. Ordinary M2 primary guards не сняты. Secondary Give Ground и явная цепочка secondary последствий в любом порядке теперь реализованы.

## Явная цепочка secondary последствий

Реализована 2026-09-28. Непосредственно проверены BOOK-PLAYER-GUIDE 1.4, Rules / Giving Ground, стр. 119, и BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91. Порядок caller выбирает явно; новое обязательное упорядочивание из книг не выводится.

`NpcNearbyConsequenceChain(batch, initial_spatial_state, steps=())` в domain/npc_nearby_consequence_models.py — frozen журнал полных NpcNearbyDefeatAcknowledgementResult и NpcNearbyGiveGroundConsumptionResult ровно одного primary-bound batch. Начало — точный batch.state и explicit spatial snapshot того же раунда с согласованными roster sides. Empty/partial chain допустимы. Каждый шаг требует тот же полный batch, exact roster/history предыдущего шага, а движение — также exact spatial. Подтверждение defeat сохраняет spatial неизменным. `.state`, `.spatial_state`, `.pending_targets` и `.acknowledgements` вычисляются по полным источникам, независимо supplied итогов нет. Primary pending/round/receipt/reload сохраняются в источнике, не переносятся автоматически.

Defeat acknowledgement и обе Give Ground request формы получили optional `continuation: NpcNearbyConsequenceChain`. Он доказывает текущее состояние после любых предшествующих последствий этого batch. Existing target/actor/GM/Stagger/once-per-round guards остаются. Give Ground принимает либо legacy previous movement, либо continuation; одновременная передача запрещена. Executor переносит continuation в completed consumption source. Defeat pending view теперь исключает и уже исполненные Give Ground цели, поэтому погашенные pending не возвращаются после позднего acknowledgement.

`apply_npc_nearby_consequence(current, spatial_state, chain, result)` в rules/npc_nearby_consequence_resolution.py сначала сверяет оба текущих snapshot и полный prefix источника шага, затем вызывает один existing apply consumer и возвращает новую chain. Caller сохраняет её вместе с `.state` и `.spatial_state`. Цепочка проверяется без повторных RNG/Attack/Stagger/Wound/Condition/movement reducers. Dispositions нельзя подменять даже при равных конечных roster/spatial: continuation обязан содержать ровно предшествующие полные steps. Пропуски, перестановки, повторные результаты, чужой batch и stale spatial отклоняются до consumer. Результаты старых standalone контрактов также могут составить цепочку при точной непрерывности; шаг previous обязан совпадать с последним полным шагом журнала.

Техническая граница «сначала defeat, потом движения» снята для continuation. Остались прежние границы: standalone batch без primary не подходит; Close Range список и начальный spatial supplied; self-defeat не поддержан; полного отката caller-owned snapshots этот локальный контракт не предотвращает. Нет автоматического порядка, discovery, battle aggregate или снятия ordinary M2 secondary guards. Source-bound погашение первичного nearby trigger после завершённой цепочки теперь реализовано отдельным consumer ниже.

9 unit tests в [test_m2_npc_nearby_consequences.py](../../tests/unit/test_m2_npc_nearby_consequences.py): 108 сочетаний для двух defeat и движения, шесть порядков двух движений и defeat, full decision prefix, stale/foreign/replay/пропуск/перестановка, сохранение pending/history/usage, legacy results, типы и immutable inputs. [Blunderbuss integration](../../tests/integration/test_m2_blunderbuss_secondary_roster.py) добавляет 12 сочетаний: оба порядка × три dispositions × safe/enemy Zone, по одному movement и каждому apply consumer, без новых Attack/RNG. Полный набор: 1682 tests OK на Python 3.14.

## Завершение nearby trigger в очереди раунда

Реализовано 2026-09-28. Источники непосредственно сверены: BOOK-PLAYER-GUIDE 1.4, Equipment / Ranged Weapons / Blunderbuss, стр. 95; Rules / Giving Ground, стр. 119; BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91. Нового игрового эффекта нет: completed secondary последствия позволяют погасить исходный trigger.

`NpcNearbyCompletionRequest(id, current, spatial_state, chain)` в domain/npc_nearby_completion_models.py требует полный NpcNearbyConsequenceChain без pending_targets. Current — NpcRoundRequest с exact chain.state и post-primary Attack round; spatial обязан совпадать с chain.spatial_state. Primary берётся из полного batch source. Очередь содержит ровно один matching NearbyTargetsStaggerRequest и сохраняет все primary follow-ups в исходном порядке (другие queued items между ними допустимы). Частичная цепочка, missing/duplicate/foreign trigger, потеря/перестановка primary follow-ups и stale roster/history/round/spatial отклоняются. Empty batch и fresh Stagger batch без pending допускают пустой steps tuple.

`complete_npc_nearby_consequences` возвращает frozen NpcNearbyCompletionResult с полным source_request. `.continuation` удаляет ровно matching trigger из текущей очереди и дополняет ordered unique `NpcRosterAttackState.completed_nearby_stagger_sources`. Это отдельная история завершения эффекта, не consumed_nearby_stagger_sources (исполнение batch), не новый receipt и не acknowledgement primary Wound. Каждая запись требует уже consumed source. Ключом служит исходный effect (resolution ID + rule ID), поэтому новые completion/batch IDs и повторная постановка trigger не обходят replay. Предыдущие histories и roster сохраняются.

`apply_npc_nearby_completion(current, spatial_state, result)` из rules/npc_nearby_completion_resolution.py сверяет оба точных текущих snapshot, повторно проверяет completion history и возвращает `(result.continuation, result.spatial_state)`. Никаких Attack/Stagger/Wound/Condition/movement reducers, RNG или повторных apply secondary шагов нет. Result сохраняет полную цепочку с decisions и primary source/receipt/reload. Spatial/usage остаются прежними. Остальные pending сохраняют порядок и продолжают блокировать coordinator; при пустой очереди coordinator закрывает уже исполненный primary ход без повторной Attack.

Техническая граница этого consumer: остальные primary follow-ups ещё не погашены и current round точно равен post-primary round; произвольные промежуточные primary transitions не допускаются. Это не новый книжный порядок. Primary исполнение и первоначальный перенос в M2 теперь доступны через отдельный Blunderbuss executor ниже; ordinary M2 secondary guards не сняты. Полный откат caller-owned snapshots не предотвращается. Узкий профильный primary Blunderbuss executor теперь возвращает полный source и pending без ручной сборки.

8 unit tests в [test_m2_npc_nearby_completion.py](../../tests/unit/test_m2_npc_nearby_completion.py): mixed/partial/empty/fresh batch, source/queue/round/spatial/history, replay с requeued trigger и relabelled batch, prior history, immutable/type guards. [Интеграция](../../tests/integration/test_m2_blunderbuss_secondary_roster.py) переносит обе очередности × три dispositions × safe/enemy Zone в round pending и проверяет остановку на сохранённой primary Wound. Новый отдельный test после fresh primary/secondary Stagger снимает единственный trigger и возобновляет coordinator: один kernel/secondary resolver, 8 RNG основной атаки, ни одного движения или повторной Attack. Полный набор: 1691 tests OK на Python 3.14.

## Профильная primary Blunderbuss Attack M2

Реализовано 2026-09-28. Непосредственно сверены BOOK-PLAYER-GUIDE 1.4, Equipment / Ranged Weapons, стр. 94–95, Rules / Attack Tests, стр. 118–119; BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91, Understanding NPC Profiles, стр. 93. Последний источник прямо разделяет числовые NPC profiles и преимущества оружия PC; автоматическое наследование свойств по имени недопустимо. Lore NPC — явный supplied факт по решению GM, не вывод из отсутствующего поля каталога.

`NpcBlunderbussAttackExecutionRequest(id, current, weapon_state, attack_profile_id, protection, preparation)` в domain/npc_blunderbuss_models.py принимает текущий NpcRoundRequest, current ReloadableWeaponState и полные ProtectionPreparationResult/RangedWeaponAttackPreparationResult. Явный available attack_profile_id должен ссылаться на supplied NPC profile с Shooting, Dam 4, Optimum Short–Short, 2H, без ignores-armour и ровно canonical Blunderbuss NearbyTargetsStaggerSpec. Inline Test берётся из этого профиля. Это узкий opt-in к полному weapon pipeline, а не автоматическая конверсия существующего NPC Warbow или назначение свойств по строковому имени. Нового канонического NPC-профиля не добавлено; integration fixture задаёт отдельное scenario equipment.

Preflight требует пустые pending, undefeated Minion actor/target, доступный профиль и отсутствие Broken/Defenceless у actor; точные round/actor/slot, неисполненный standard Attack slot и неприменённый execution ID. Protection проверяется по target ID, его Conditions/equipment и числовым Test profiles; baseline Attack — по actor Staggered, Damage/Resilience и исходным Tests, без дополнительных effects/immunity. Kernel должен содержать только этот baseline, текущее target injury и explicit can-leave/once-per-round факты. Current weapon обязан точно совпадать с preparation source и иметь Blunderbuss ID; loaded/Lore/Close enemy/Maximum Range/reload cycle проверяет прежняя preparation.

Weapon preparation единолично добавляет +2d Short, –1d вне Optimum, Nearby trigger и reload rules. Baseline Protection не проходит generic NPC range preparation; NPC_OUTSIDE_OPTIMUM_RULE_ID в baseline запрещён, поэтому штраф не дублируется и generic GM approval для 2H не подменяет фиксированный Medium Max Blunderbuss. Остальные contextual Test modifiers/awareness supplied. Aim composition, произвольные дополнительные effects/kernel options, другой NPC damage/range/traits и не-Minion участники вне этого среза отклоняются явно.

`execute_npc_blunderbuss_attack(request, rng, decisions=...)` вызывает ровно один existing execute_prepared_ranged_weapon_attack после общего preflight. Result хранит полный PreparedRangedWeaponAttackExecutionResult; `.primary_attack` возвращает полный RangedWeaponAttackExecutionResult для secondary batch binding, `.weapon_state` — готовый reload transition, `.applied_rule_ids` сохраняет profile/Protection/preparation/execution trace. `.continuation` переносит только primary target injury, post-Attack round/receipt, всю pending очередь и один consumed execution ID, сохраняя остальные histories. Blunderbuss не стреляет в Close, поэтому miss не требует переноса attacker Staggered.

`apply_npc_blunderbuss_attack(current, weapon_state, result)` сверяет exact current round/roster/history и weapon snapshot, проверяет replay и возвращает `(result.continuation, result.weapon_state)`. Caller сохраняет оба snapshot и полный result. Secondary pipeline, movement, decisions и completion по-прежнему исполняются отдельно; primary injury/history больше не собираются вручную. Weapon остаётся отдельным snapshot без общего battle aggregate. Полный откат caller-owned snapshots не предотвращается.

Ordinary M2 Attack/controller/runner journal guards не расширены: новый executor — отдельная явная граница. Primary defeat теперь подтверждается отдельным consumer по полным Blunderbuss и secondary completion results (ниже); primary Give Ground теперь обрабатывается отдельным adapter после secondary completion (ниже). Старые ordinary-result consumers не расширены. Следующий срез — подключение Blunderbuss к координации одного раунда M2. Автоматического Close Range discovery, Reload, победы или выбора исходов нет.

8 unit tests в [test_m2_npc_blunderbuss.py](../../tests/unit/test_m2_npc_blunderbuss.py): hit/miss, Short/Medium/Staggered, один kernel/receipt/reload, exact source/Protection/slot/profile/weapon, pending/Conditions/availability, replay, все histories, immutable/type guards и запрет дублирующего range modifier. [Интеграция](../../tests/integration/test_m2_blunderbuss_secondary_roster.py) теперь выполняет новый primary executor → secondary batch → chain → completion: empty/fresh/mixed, safe/enemy и три dispositions в обоих порядках. Один kernel и 8 RNG основной атаки; нет ручного primary injury/history transfer. Полный набор: 1700 tests OK на Python 3.14.

## Подтверждение primary defeat после secondary completion

NpcBlunderbussDefeatAcknowledgementRequest связывает полный NpcBlunderbussAttackExecutionResult, NpcNearbyCompletionResult, текущий NpcRoundRequest, SpatialBattleState и прежний MinionDefeatDecision. Сравниваются полный primary ranged result и начальный post-primary roster/history secondary batch; ID раундового запроса и actor_order также должны совпадать. Текущие round/roster/history/pending/spatial должны точно соответствовать continuation завершённой secondary chain. Это отдельный consumer: ordinary MinionDefeatAcknowledgementRequest сохраняет прежний контракт.

Проверяются attacker/primary target, GM approval, новая Wound ранее не defeated Minion, полный profile_wound/state_change и конечная injury основной цели. Равный secondary ProfileStateChangeRequest не подменяет primary источник. В общей pending queue допустим ровно один matching primary defeat; неоднозначные дубликаты отклоняются. Подтверждение после secondary completion — технический порядок этого adapter, не новое игровое правило.

acknowledge_npc_blunderbuss_defeat возвращает frozen source-bound result. apply_npc_blunderbuss_defeat требует точных текущих snapshots, удаляет ровно primary follow-up и добавляет Attack request ID в существующий acknowledged_defeat_execution_ids. Replay проверяется до stale snapshots и блокирует новый acknowledgement ID, замену disposition и requeued pending. Все остальные histories/pending, roster/round/spatial и полные secondary decisions сохраняются. weapon_state — read-only представление исходного Attack result, без нового перехода оружия. RNG, Wound, Stagger и движение не вызываются. Exclusion defeated остаётся отдельным явным действием.

Источники непосредственно перечитаны: BOOK-GM-GUIDE 1.1, Allies and Antagonists / Minions, стр. 91; BOOK-PLAYER-GUIDE 1.4, Equipment / Ranged Weapons / Blunderbuss, стр. 95. RULE-NPC-002 сохранён: атакующий выбирает killed, knocked out либо disarmed/surrender с одобрением GM; выбор не создаёт дополнительную injury/Conditions.

[8 unit tests](../../tests/unit/test_m2_npc_blunderbuss_defeat.py) проверяют все три независимых primary/secondary dispositions, равные follow-ups, empty batch, сохранение прочих pending и источников, GM/target/source guards, stale/replay/requeued/ambiguous pending и неизменяемость. [Integration](../../tests/integration/test_m2_blunderbuss_secondary_roster.py) покрывает 36 сочетаний, явное исключение обеих defeated целей и round resume: один primary kernel, 8 RNG, один secondary resolver. Полный набор: 1708 tests OK на Python 3.14. Primary Give Ground подключён отдельным adapter ниже; controller/runner journal ещё не принимают этот вид атаки.

## Primary Give Ground после secondary completion

NpcBlunderbussGiveGroundExecutionRequest связывает полный NpcBlunderbussAttackExecutionResult, NpcNearbyCompletionResult, текущий NpcRoundRequest, SpatialBattleState и явный GiveGroundResolutionRequest. ConsumptionRequest принимает те же источники с готовым GiveGroundResolutionResult. Оба запроса frozen; проверяется полный primary ranged result, исходный post-primary roster/history secondary batch, ID раундового запроса/actor_order и точные post-completion current/spatial. Старый ordinary NpcGiveGround consumer не расширяется.

Требуются завершённый primary выбор StaggerChoice.GIVE_GROUND с допустимым outcome, неизменная injury основной цели, единственный matching GiveGroundRequest и его сохранение ровно один раз в pending. Mover — primary target, away_from — primary actor, Conditions взяты из текущего roster. Kernel availability и spatial.gave_ground_entity_ids должны разрешать отход; spatial round и стороны соответствуют roster. Вторичный Give Ground другого участника не расходует возможность основной цели. Маршрут задаётся явно: прежний resolver проверяет adjacent/away-from, Prone/Defenceless, obstacles, Difficult Terrain и enemies на пути.

execute_npc_blunderbuss_give_ground выполняет preflight контекста, один resolve_give_ground и один consume_npc_blunderbuss_give_ground. Подменённый источник результата отклоняется. ConsumptionResult хранит полный completed movement и вычисляет continuation: переносит Conditions основной цели, дописывает Attack ID в существующий consumed_give_ground_execution_ids, удаляет ровно primary pending. spatial_state берётся из movement; weapon_state — read-only view исходного Attack. Остальные участники, histories, secondary decisions, receipt/reload и pending сохраняются. Broken определяется по фактическому post-secondary spatial, включая вторичные цели, уже переместившиеся в destination.

apply_npc_blunderbuss_give_ground требует exact current/spatial и возвращает оба новых snapshots; replay по Attack ID отклоняется до stale проверки, в том числе с новым request ID и requeued pending. Consumption и application не исполняют movement/Conditions/Wound/RNG повторно. Caller сохраняет returned snapshots и полные результаты; полного отката всех caller-owned snapshots этот локальный контракт не предотвращает. Требование secondary completion перед primary movement — техническая граница adapter, не книжный порядок последствий.

Источники непосредственно перечитаны: BOOK-PLAYER-GUIDE 1.4, Rules / Giving Ground, стр. 119; Equipment / Ranged Weapons / Blunderbuss, стр. 95. [10 unit tests](../../tests/unit/test_m2_npc_blunderbuss_give_ground.py) покрывают safe/enemy/уже Broken, изменения destination из-за secondary movement, empty batch, сохранение решений/history/pending/weapon, source/choice/type/once-per-round/replay guards, пути и исключения. [Integration](../../tests/integration/test_m2_blunderbuss_primary_give_ground.py) проверяет 12 сочетаний порядка secondary последствий, dispositions и safe/enemy destination: Attack → secondary chain → completion → primary movement → explicit secondary exclusion → round resume. Один primary kernel, 8 RNG, один secondary resolver и по одному movement каждой цели. Полный набор: 1719 tests OK на Python 3.14. Controller/runner journal пока не подключены; автоматический выбор последствий, Reload и общий battle aggregate отсутствуют.
