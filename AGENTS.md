# Инструкции для работы с репозиторием

## Перед началом задачи

1. Проверить `git status`, не перезаписывать несвязанные изменения пользователя.
2. Прочитать `README.md`, `docs/project-status.md` и короткий индекс `docs/open-questions.md`.
3. Прочитать `docs/source-policy.md` при входе в новую сессию; применять иерархию источников во всех задачах.
4. Дальнейшее чтение выбирать по задаче через `docs/README.md`: правила/книга — для механики, архитектура и относящиеся ADR — для изменения взаимодействий. Подробности вопросов читать только по затронутой теме. Исторические обзоры не входят в обязательный старт.
5. В рамках сессии переиспользовать уже прочитанный неизменившийся контекст. После внешних изменений проверить актуальный diff и перечитать затронутые инструкции/статус; не полагаться на прежнее состояние другой сессии.

В больших каталогах (`source-index`, `rule-traceability`, подробный kernel) сначала найти нужные Rule ID/раздел через `rg`, затем читать относящийся фрагмент. Не загружать весь справочник для локального изменения.

Player’s Guide1.4 и Gamemaster’s Guide1.1 — главные источники правил. `docs/game-rules.md`, дизайн-док, код и тесты прототипа могут быть заменены при конфликте с книгами. Отклонение допустимо только как явно подтверждённый пользователем house rule с записью в документации. При извлечении правила сохранять книгу, главу и страницу; лор и пример не считать нормативным правилом без основания.

## Работа с Git

- Не выполнять `git commit` и `git push`: это делает пользователь.
- Не добавлять PDF книг в `.gitignore`: пользователь сам следит за их исключением из репозитория.
- Разрешены read-only команды Git для состояния и просмотра изменений.

## Архитектурные ограничения

- Домен и движок не зависят от CLI/JSON/GUI или балансировщика. Описание бойца отделено от состояния конкретного боя.
- RNG передаётся явно; глобальный `random` в правилах не используется. Балансировщик получает вход симулятора и агрегированный результат.
- Простые правила реализовывать явно и типизированно. Не создавать универсальный язык правил или шину событий без потребности.
- Новое поведение проверять детерминированно. Статистический тест не ожидает точное Monte Carlo-значение. Сохранять проверки полного источника, однократного применения и целостности результатов.
- Публичный контракт и относящееся решение обновлять вместе с реализацией.

## Контракты во время разработки

Поддерживать один актуальный формат каждой family: Magic JSON6, у остальных families — собственный формат1. Обратная совместимость разработки не нужна: обновлять код/схемы/примеры/тесты вместе, удалять устаревшие ветви и compatibility-only проверки. Не вводить deprecated-период без запроса пользователя. Новое правило само по себе не требует нового wire version. Стратегию внешних версий определить перед выпуском.

Старые ADR/аудиты сохраняют историю, но не требуют исполнения прежних форматов. Общие schema fragments отделены от удалённых версий. Уникальные проверки правил и валидации сохраняются в текущем контракте.

## Автономная работа до согласованной вехи

- Планировать веху как законченную функцию через необходимые слои. Внутренние шаги: условия допуска/тестовые случаи → модели и исполнение → интеграция → адресная проверка. Не превращать каждый слой в отдельную документальную веху. Сохранять границы принятых решений и очередность roadmap.
- Выполнять порученную веху до проверяемого результата без просьб «продолжаем». После шага запускать нужные проверки, кратко сообщать результат и переходить дальше. При ошибке установить причину и исправить её в рамках контракта.
- Спрашивать при существенной неоднозначности правил, смене согласованного контракта или блокере с решением пользователя. Не выдумывать house rule.
- Небольшую задачу выполнять одним агентом. Одного-двух сабагентов привлекать только для действительно независимой работы, где выигрыш превышает координацию: сверка источников, отдельные файлы, ревью. Третий допустим для отдельной оправданной задачи. Не делегировать ради самого параллелизма.
- До делегирования согласовать интерфейс и владение файлами. Зависимые изменения выполнять последовательно; общие документы/интеграция — ответственность главного агента. Проверять выводы по источникам и исполнению. Не запускать одновременно несколько тяжёлых тестовых прогонов на одной машине без основания ожидать выигрыш; согласовывать общий план проверок.

## Документация и ADR

- ADR нужен для существенного выбора между альтернативами, изменения инварианта, ответственности слоя или публичной границы. Добавление правила по существующему образцу, refactor helper и обновление статуса обычно отдельного ADR не требуют. Для одной функции достаточно одного ADR, если он нужен; история шагов остаётся в Git.
- У каждого факта одно основное место. `project-status.md` — актуальный этап, ограничения, последняя проверка и следующий шаг; `open-questions.md` — индекс незакрытых вопросов и действующих допущений; roadmap — очередь функций. Исторические результаты — в ADR/аудите/архиве, без копирования в обзоры.
- Механика: обновить соответствующее правило, тесты и статус. Архитектура: затронутый раздел обзора/ADR при новом решении. Публичный API/CLI: текущий контракт и пользовательские примеры. README/индекс менять только при изменении навигации или пользовательского входа.
- `source-index.md` менять при новом источнике/чтении/версии; `rule-traceability.md` — при новых связях правила и реализации; `contradictions.md` — при реальном расхождении. Не обновлять их автоматически для engineering-only изменений. Roadmap менять при изменении очереди/scope.
- Не создавать новый отчёт аудита и standalone public probe для каждого внутреннего перехода. Использовать существующие тесты; публичный пример добавлять для полезной пользовательской возможности. Подробный отдельный отчёт нужен, когда это помогает проверить значимую границу.

## Политика проверок

- По умолчанию — тесты изменённого поведения и ближайших зависимых компонентов. Для законченной функции добавить нужные проверки подсистемы/сквозного пути. Выбирать по рискам и зависимостям, не только по именам файлов.
- Полный regression — в контрольной точке проекта: несколько связанных функций, существенное изменение общего ядра/контракта с широкими зависимостями, выявленный риск вне подсистемы либо явный запрос. Перед дорогим прогоном назвать основание и объём; отдельного разрешения не нужно. ADR, небольшой шаг или передача сессии сами по себе не являются основанием.
- Wheel/fresh-installed checks — при изменении сборки, dependencies, package discovery/resource inclusion, установки/entry points, риске зависимости от source tree либо перед выпуском. Новая схема при прежнем `*.json` discovery не требует сборки: проверить source/offline refs, доставку — в соответствующей контрольной точке.
- Документация: согласованность и ссылки. Изменённая CLI help — адресная проверка. Игровые тесты/wheel ради текста не запускать; исполняемые примеры проверять, когда менялся их код/контракт.
- Unit проверяет правило/границы, integration — взаимодействие, installed — доставку. Полную module/console×sequential/process матрицу оставлять на репрезентативных сценариях при изменении механизма, не повторять для каждого правила.
- После исправления повторять упавшие и затронутые зависимые проверки. Успешные дорогие проверки не повторять без влияющего изменения, сбоя или риска. Учитывать известные ошибки отдельно; адресный/составной результат не выдавать за единый зелёный full run.
- Повторяющуюся подготовку состояний выносить в небольшие явные `tests/support` builders при реальном повторном использовании. Каждый вызов возвращает независимые данные; helpers не исправляют malformed source и не вычисляют ожидаемый результат копированием production-алгоритма. Универсальный fixture DSL и массовая миграция тестов без задачи не нужны.
- В ADR, если он нужен, указывать адресный план проверки. Старые списки приёмки не копировать; незавершённый план со старым full/wheel требованием явно привести к этой согласованной политике, сохранив игровые границы. Перенесённую необходимую проверку и её контрольную точку записать в статусе.

Адресная команда (модули выбирать по задаче):

```powershell
$env:PYTHONPATH = 'src'
.venv/Scripts/python.exe -m unittest tests.unit.test_k1_opposed_test -v
```

Полный набор при наличии основания: `.venv/Scripts/python.exe -m unittest discover -s tests -v`. При отсутствии `.venv` использовать Python3.12+ с зависимостями проекта (`py -3.12` на Windows).

## Протокол завершения сессии

По просьбе пользователя подготовить передачу обновить статус и изменившиеся открытые вопросы: что сделано, ограничения, фактические команды/результаты, точный следующий шаг. Остальные документы менять только по матрице выше. Проверить изменённые ссылки и необходимые тесты; повторный full/wheel ради завершения сессии не нужен. Сообщить незакоммиченные файлы, не выполнять commit/push.

Не хранить стенограммы чатов. Следующей сессии должны быть достаточны актуальный статус, индекс вопросов и относящиеся правила/ADR/тесты.
