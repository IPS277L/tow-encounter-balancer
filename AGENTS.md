# Инструкции для работы с репозиторием

## Перед началом задачи

1. Прочитать `README.md`.
2. Прочитать `docs/project-status.md` и `docs/open-questions.md`.
3. Прочитать `docs/source-policy.md` и применить указанную там иерархию источников.
4. Для изменений механики свериться с одобренными материалами в `docs/rules/` и прототипом в `docs/game-rules.md`.
5. Для архитектурных изменений прочитать `docs/architecture/overview.md` и относящиеся к задаче ADR из `docs/decisions/`.
6. Проверить `git status` и не перезаписывать несвязанные пользовательские изменения.

Player’s Guide и Gamemaster’s Guide выбранной редакции являются главными источниками игровых правил. Текущие `docs/game-rules.md`, дизайн-док, код и тесты описывают упрощённый прототип и могут быть заменены. При расхождении с книгами нельзя сохранять прототип только ради обратной совместимости. Исключение возможно лишь для явно подтверждённого пользователем house rule; отклонение от книг нужно документировать.

При извлечении правил обязательно сохранять ссылку на источник: идентификатор книги, главу и страницу. Не считать художественный текст, описание мира или пример нормативным правилом без явного основания.

## Работа с Git

- Не выполнять `git commit` и `git push`: пользователь самостоятельно создаёт и отправляет коммиты.
- Не добавлять PDF книг в `.gitignore`; пользователь самостоятельно следит, чтобы исходные книги не попали в репозиторий.
- Разрешены read-only команды Git для проверки состояния и просмотра изменений.

## Архитектурные ограничения

- Домен и движок не зависят от CLI, JSON, GUI или балансировщика.
- Описание бойца отделено от изменяемого состояния конкретного боя.
- Случайность передаётся через внедряемый источник RNG; глобальный `random` в правилах не используется.
- Балансировщик получает только вход симулятора и агрегированный результат.
- Простые правила реализуются явно и типизированно. Не создавать универсальный язык правил или сложную шину событий без реальной потребности.
- Новое поведение сопровождается детерминированными тестами. Статистические тесты не должны ожидать точное Monte Carlo-значение.
- Публичные контракты и решения документируются одновременно с реализацией.

## Контракты во время разработки

- Поддерживать один актуальный формат каждой внешней JSON/API family. У Magic это `schema_version="6"`; единственные версии других families не меняются ради выравнивания номера.
- Обратная совместимость с прежними форматами разработки не требуется. При изменении контракта одновременно обновлять код, схемы, примеры и содержательные тесты; удалять устаревшие парсеры, схемы, миграции и проверки совместимости. Не вводить deprecated-период без отдельного требования пользователя.
- Новая игровая механика сама по себе не требует новой версии JSON. В разработке допускаются несовместимые изменения текущего формата; отдельную стратегию версий определить перед внешним выпуском.
- Старые ADR и отчёты сохраняют историю решений и фактических проверок, но не требуют исполняемой поддержки старых форматов. Текущий контракт задают актуальные схемы и последнее заменяющее решение. Общие используемые schema fragments хранить отдельно от удалённых версий.
- Удалять проверки только устаревшего формата и дубли; сохранять уникальные проверки правил, строгой валидации, источников, ошибок и целостности результатов в актуальном контракте.

## Автономная работа до согласованной вехи

- Получив поручение на веху, выполнять её до проверяемого результата без запроса «продолжаем» между внутренними шагами. Сохранять небольшие изменения: контракт и модели → исполнение → интеграция → аудит. Порядок roadmap и границы принятого ADR сохраняются.
- После каждого шага запускать релевантные детерминированные проверки и сообщать краткий результат; к следующему шагу переходить самостоятельно. При новой ошибке сначала установить причину и исправить её в рамках контракта.
- Останавливаться для вопроса при существенной неоднозначности правил, необходимости изменить согласованный контракт или блокере, требующем решения пользователя. Не придумывать house rule для продолжения.
- Использовать одного-двух сабагентов, когда независимые проверки или задачи действительно могут идти параллельно: сверка источников/контракта, тестовые случаи, ревью. Главный агент отвечает за архитектуру, интеграцию и итоговый diff. Дополнительный сабагент допустим для отдельной независимой задачи.
- До параллельной реализации согласовать интерфейс и разделить владение файлами. Не поручать нескольким агентам запись в один файл; зависимые шаги выполнять последовательно. Общие документы и итоговый статус обновляет главный агент. Выводы сабагентов проверять по источникам и исполняемым тестам.
- Объём проверок выбирать по разделу «Политика проверок» ниже. Завершение шага, создание ADR и завершение небольшой вехи сами по себе не требуют полной регрессии или сборки wheel.
- `docs/project-status.md` содержит только актуальный этап, ограничения, последнюю проверку и точный следующий шаг. `docs/open-questions.md` содержит незакрытые вопросы и действующие временные допущения. Исторические отчёты сохранять в отдельных архивных документах со ссылками; не наращивать ими актуальный контекст.

## Политика проверок

Согласована с пользователем 2026-11-03. Различать рабочий шаг (небольшое изменение), функциональную веху (связное поведение) и контрольную точку проекта (объединение нескольких вех, существенные изменения общего ядра или подготовка выпуска).

- По умолчанию запускать детерминированные тесты изменённого поведения и ближайших зависимых компонентов. Для функциональной вехи расширять набор до затронутой подсистемы и нужных сквозных сценариев. Выбирать набор по зависимостям и рискам, а не только по именам изменённых файлов.
- Полную регрессию проводить в контрольной точке проекта, при существенном изменении общего ядра/публичного контракта с широкими зависимостями, выявленном риске за пределами подсистемы или по явному запросу пользователя. Перед дорогим прогоном кратко сообщать основание и объём. Не запрашивать отдельное разрешение на обоснованную проверку.
- Wheel и fresh-installed audit нужны при изменении сборки, зависимостей, package discovery, правил включения ресурсов, установки/entry points, при риске зависимости от source tree или перед выпуском. Выбирать адресные installed checks для затронутой границы. Добавление очередного модуля/JSON Schema при прежнем механизме упаковки не требует автоматической пересборки: проверить source imports/offline refs и перенести проверку доставки пакета в контрольную точку.
- Для изменений только документации проверять согласованность и локальные ссылки. Запускать исполняемые примеры, если менялся их код или проверяемый ими контракт. Не запускать игровые тесты и wheel ради текста или справки; изменённую CLI-справку проверять адресно.
- Избегать дублирования одного доказательства в unit/integration/public example/installed checks. Unit проверяет правило и границы, integration — взаимодействие, installed — доставку и запуск пакета. Полную матрицу module/console × sequential/process проверять на выбранных репрезентативных сценариях при изменении соответствующего механизма, а не для каждого нового правила.
- После исправления ошибки повторять упавший тест и релевантные зависимые проверки. Уже успешные дорогие проверки повторять лишь при новом влияющем изменении, сбое или неразрешённом риске. Изменение текста не обнуляет предыдущие результаты исполнения.
- В новых ADR указывать адресный план проверки и основание для full/installed audit, если он нужен. Исторические списки приёмки не копировать автоматически. Для незавершённого контракта со старым требованием полного аудита явно обновить его план по этой согласованной политике, сохранив игровые и архитектурные границы; не переписывать исторические результаты закрытых ADR.
- В отчёте указывать фактически выполненные команды, объём и ограничения проверки; перенесённые full/installed проверки и ближайшую контрольную точку записывать в `docs/project-status.md`, если они актуальны. Не выдавать адресный или составной результат за единый зелёный full run. Известные ошибки окружения учитывать отдельно.

## Команды проверки

Адресная проверка (пример; модули выбирать под задачу):

```powershell
$env:PYTHONPATH = "src"
.venv/Scripts/python.exe -m unittest tests.unit.test_k1_opposed_test -v
```

Полный набор — только по основаниям из политики выше:

```powershell
$env:PYTHONPATH = "src"
.venv/Scripts/python.exe -m unittest discover -s tests -v
```

При отсутствии `.venv` использовать доступный Python 3.12+ с зависимостями проекта (`py -3.12` на Windows).

## Протокол завершения сессии

Этот протокол выполняется, когда пользователь в конце сессии просит обновить контекст, документацию, статус или подготовить передачу работы следующей сессии.

1. Обновить `docs/project-status.md`: что сделано, текущий этап, известные ограничения, последняя проверенная команда и точный следующий шаг.
2. Обновить `docs/open-questions.md`: удалить закрытые вопросы, добавить новые и записать безопасные временные допущения.
3. Если менялись правила, синхронизировать `docs/game-rules.md` и тесты.
4. При работе с книгой обновить `docs/source-index.md`, `docs/rule-traceability.md` и `docs/contradictions.md`.
5. Если принято нетривиальное архитектурное решение, создать или обновить ADR в `docs/decisions/`.
6. Если изменился порядок этапов, обновить `docs/roadmap.md`.
7. Проверить ссылки в `README.md` и `docs/README.md`.
8. Выполнить необходимые проверки по политике выше и записать результат в `docs/project-status.md`. Передача сессии сама по себе не требует full regression или wheel audit.
9. Сообщить пользователю незакоммиченные файлы. Не выполнять commit или push.

Не хранить стенограммы чатов. Для продолжения работы должны быть достаточны актуальный статус, открытые вопросы, правила, ADR и тесты.
