# Инструкции для работы с репозиторием

## Перед началом задачи

1. Прочитать `README.md`.
2. Прочитать `docs/project-status.md` и `docs/open-questions.md`.
3. Прочитать `docs/source-policy.md` и применить указанную там иерархию источников.
4. Для изменений механики свериться с одобренными материалами в `docs/rules/` и прототипом в `docs/game-rules.md`.
5. Для архитектурных изменений прочитать `docs/architecture/overview.md` и относящиеся к задаче ADR из `docs/decisions/`.
6. Проверить `git status` и не перезаписывать несвязанные пользовательские изменения.

Player’s Guide и Gamemaster’s Guide выбранной редакции являются главными источниками игровых правил. Текущие `docs/game-rules.md`, дизайн-док, код и тесты описывают упрощённый прототип и могут быть заменены. При расхождении с книгами нельзя сохранять прототип только ради обратной совместимости. Исключение возможно лишь для явно подтверждённого пользователем house rule; отклонение от книг нужно документировать.

При извлечении правил обязательно сохранять ссылку на источник: идентификатор книги, главу и страницу. Не считать художественный текст, описание мира или пример нормативным правилом без явного основания.

## Работа с Git

- Не выполнять `git commit` и `git push`: пользователь самостоятельно создаёт и отправляет коммиты.
- Не добавлять PDF книг в `.gitignore`; пользователь самостоятельно следит, чтобы исходные книги не попали в репозиторий.
- Разрешены read-only команды Git для проверки состояния и просмотра изменений.

## Архитектурные ограничения

- Домен и движок не зависят от CLI, JSON, GUI или балансировщика.
- Описание бойца отделено от изменяемого состояния конкретного боя.
- Случайность передаётся через внедряемый источник RNG; глобальный `random` в правилах не используется.
- Балансировщик получает только вход симулятора и агрегированный результат.
- Простые правила реализуются явно и типизированно. Не создавать универсальный язык правил или сложную шину событий без реальной потребности.
- Новое поведение сопровождается детерминированными тестами. Статистические тесты не должны ожидать точное Monte Carlo-значение.
- Публичные контракты и решения документируются одновременно с реализацией.


## Протокол завершения сессии

Этот протокол выполняется, когда пользователь в конце сессии просит обновить контекст, документацию, статус или подготовить передачу работы следующей сессии.

1. Обновить `docs/project-status.md`: что сделано, текущий этап, известные ограничения, последняя проверенная команда и точный следующий шаг.
2. Обновить `docs/open-questions.md`: удалить закрытые вопросы, добавить новые и записать безопасные временные допущения.
3. Если менялись правила, синхронизировать `docs/game-rules.md` и тесты.
4. При работе с книгой обновить `docs/source-index.md`, `docs/rule-traceability.md` и `docs/contradictions.md`.
5. Если принято нетривиальное архитектурное решение, создать или обновить ADR в `docs/decisions/`.
6. Если изменился порядок этапов, обновить `docs/roadmap.md`.
7. Проверить ссылки в `README.md` и `docs/README.md`.
8. Запустить релевантные тесты и записать результат в `docs/project-status.md`.
9. Сообщить пользователю незакоммиченные файлы. Не выполнять commit или push.

Не хранить стенограммы чатов. Для продолжения работы должны быть достаточны актуальный статус, открытые вопросы, правила, ADR и тесты.
